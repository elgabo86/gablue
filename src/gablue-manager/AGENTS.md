# Gablue Manager — paquet `gablue_manager` (src/gablue-manager)

GUI PySide6 (Wayland natif) : liste des postes SSH avec état et latence, bureau distant (`gremote`), fichiers (`dolphin sftp://`), terminal SSH, arrêt / redémarrage / mise à jour des postes, découverte mDNS, import de `~/.ssh/config`, ajout + copie de clé — **et la machine courante** : serveur SSH, annonce mDNS, mises à jour (image Gablue, Flatpaks, gwine, Homebrew) et options avancées (ex-`gablue-config`), services et variante de l'image (ex-recettes ujust). Nom affiché « Gablue Manager » ; binaire et `.desktop` = `gablue-manager` / `gablue-manager.desktop` (convention `gablue-*`), **catégorie Système** (`Categories=System;`) et icône maison `gablue-manager` (`/usr/share/icons/hicolor/scalable/apps/gablue-manager.svg` : carré bleu Gablue, anneau en **engrenage à 8 dents** formant un G — ouverture en haut à droite et barre horizontale, le tout en une seule silhouette), avec repli `network-server` hors image via `uiutil.app_icon()`. Remplace l'ancien `gablue-ssh`, `/usr/libexec/gablue-config` (script kdialog supprimé, ainsi que `gablueconfig.desktop` et son entrée de blacklist) et `gablue-update` (script Python et `gablueupdate.desktop` supprimés, ainsi que son entrée de blacklist, la recette `ujust gablue-update`, l'alias `gablue-update` et la ligne d'aide correspondante) : les mises à jour se lancent depuis la carte « Ce poste ».

## Paquet

Sources = ce dossier (`src/gablue-manager/`), installées par
`files/scripts/build-manager` :

| Fichier | Rôle |
|---|---|
| `gablue-manager` | lanceur `/usr/bin/gablue-manager` : ajoute `/usr/lib/gablue-manager` (ou le dossier courant en développement) au `sys.path` puis `gablue_manager.app.main()` |
| `gablue_manager/app.py` | `HELP` et `main()` : fenêtre principale, ou modes CLI (`cli.py`) |
| `gablue_manager/cli.py` | modes `--progress`, `--confirm`, `--choose` (une boîte, sans `MainWindow` ni sondes SSH) |
| `gablue_manager/constants.py` | chemins, binaires (`_which`), couleurs et textes d'état, constantes kargs/helpers |
| `gablue_manager/util.py` | cible ssh, nom affiché, URL KIO, normalisation MAC, options ssh communes |
| `gablue_manager/hosts.py` | registre `ssh-hosts.json`, découverte mDNS, import `~/.ssh/config`, adresses du poste |
| `gablue_manager/ssh.py` | empreintes d'hôte, copie de clé, exécution distante, sudo distant |
| `gablue_manager/local.py` | état/commandes de la machine (sshd, avahi, kargs, CPUID, services, variante, atuin, gwine, booster, Tailscale) |
| `gablue_manager/apps.py` | applications AppImage (émulateurs + OpenCode 2) : état, GearLever, install/config/suppression |
| `gablue_manager/workers.py` | threads : vérification des postes, clé, commande ssh, découverte |
| `gablue_manager/style.py` | QSS adapté au thème Plasma |
| `gablue_manager/uiutil.py` | `restyle_label`, `fit_dialog_height`, `recommendation_badge` |
| `gablue_manager/tasks.py` | `start_task`, dialogues de tâche locale/distante (non modaux), séquence globale (`SequentialTaskDialog`), lien d'enregistrement (`_AuthLinkRow`) |
| `gablue_manager/widgets.py` | `BusyProgressBar`, `StatusDot`, `HostCard`, `LocalCard` |
| `gablue_manager/dialogs/` | un fichier par dialogue (`host`, `key`, `kernel`, `services`, `variant`, `gwine`, `booster`, `tailscale`, `apps`) |
| `gablue_manager/window.py` | `MainWindow` |
| `tests/` | tests unitaires stdlib des fonctions pures |

**Règle** : le paquet est la source de vérité ; ne pas réintroduire de fichier
unique assemblé. Un nouveau dialogue → un fichier dans `dialogs/` + une entrée
de menu dans `window.py`. Les imports relatifs vont dans un seul sens
(`constants ← util ← hosts/ssh/local ← workers/tasks ← dialogs ← window ← app`) :
un cycle (ex. `_ssh_opts` entre `hosts` et `ssh`) se règle en descendant la
fonction dans le module le plus bas, pas par un import tardif.

## Build

- `Containerfile-gablue` : `COPY src/gablue-manager /src/gablue-manager`, puis
  `RUN /ctx/build-manager` juste après `build-gwine`.
- `files/scripts/build-manager` : copie `gablue_manager/` dans
  `/usr/lib/gablue-manager/`, installe le lanceur en `/usr/bin/gablue-manager`
  (755) et retire les `__pycache__` (le Python du build n'est pas celui du
  poste, `/usr` est en lecture seule sur composefs).
- Développement : `src/gablue-manager/gablue-manager --help` marche depuis le
  dépôt ; `PYTHONPATH=src/gablue-manager python3 -c "import gablue_manager.app"`.
- L'image doit être reconstruite pour valider l'installation (pas l'ISO).

## Modes CLI (sans fenêtre principale)

`gablue-manager` sans argument ouvre la fenêtre principale. Trois modes
n'instancient **que** la boîte demandée : `MainWindow` n'est jamais créée, donc
aucune sonde SSH (les `CheckWorker` du timer de 30 s), aucun scan Avahi, aucun
accès au registre des postes.

| Mode | Rôle |
|---|---|
| `--progress --title T [--subtitle T] [--auto-close-success\|--auto-close] -- commande…` | `LocalTaskDialog` sur la commande (canaux fusionnés, annulation SIGTERM puis SIGKILL). La commande publie `::gablue:step n total texte`, `::gablue:busy texte` (total inconnu) et `::gablue:done [texte]` ; ces lignes de protocole sont retirées du journal (`local.parse_gablue_progress`), l'outil écrivant sa version lisible à côté. Échec → journal révélé ; `--auto-close-success` ferme la fenêtre en cas de succès. Code de sortie = celui de la commande (130 si annulé). |
| `--confirm --title T --text T [--yes T] [--no T]` | `QMessageBox` ; sortie 0 = oui, 1 = non. |
| `--choose --title T --text T --item valeur [--item valeur…]` | `QInputDialog` ; imprime la valeur choisie (libellé après une tabulation), sortie 1 si annulé. |

Sans affichage, `--progress` exécute la commande telle quelle (sans protocole)
et `--confirm` répond non : gwine reste utilisable en terminal. gwine s'en sert
au premier lancement (initialisation du préfixe dans la fenêtre de progression),
dans `conflict.sh`/`wgp/mount.sh` (oui/non) et `wgp/modes.sh` (choix de
l'exécutable d'un WGP). Les mises à jour locales de gwine dans la fenêtre
principale passent aussi `GABLUE_PROGRESS=1` et `parse_gablue_progress`, donc
la barre d'étapes remplace le journal, resté derrière « Terminal ».

## Comportement

- **Registre** `~/.config/gablue/ssh-hosts.json` (dossier 0700, fichier 0600, écriture atomique `mkstemp` + `os.replace`) : source de vérité de l'app. Un poste ajouté uniquement par `ssh-key-add` en CLI n'y figure pas (le script ne consigne rien) — d'où l'import `~/.ssh/config`. Registre illisible → renommé `ssh-hosts.corrupt-<horodatage>.json`, jamais écrasé. Champs `addresses` (adresses de secours de la même machine : LAN, Tailscale) et `active` (celle qui a répondu en dernier, utilisée par `ssh_target`/`dolphin_url`) ; l'ancien champ `mac` (Wake-on-LAN, fonction retirée le 06/11/2026) est ignoré et disparaît au premier enregistrement.
- **État** : `ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes -p N … true`, 6 postes en parallèle, relance toutes les 30 s, test annulable à la fermeture. `BatchMode` + `IdentitiesOnly` = c'est bien NOTRE clé qui est testée ; pas d'`accept-new` ici, un simple ping ne doit pas écrire dans `known_hosts`. Vert = clé acceptée, orange = joignable mais clé refusée, violet = empreinte d'hôte inconnue, gris = hors ligne / DNS. **Pas de sonde répétée des états bloqués** (`NO_AUTO_PROBE_STATES` : `auth`, `hostkey`, `penalty`) : une connexion qui se ferme avant authentification compte comme offense pour `PerSourcePenalties` (OpenSSH 9.8+ — `authfail` 5 s, blocage dès 15 s accumulées, jusqu'à 10 min), et sonder toutes les 30 s un poste qui refuse la clé finissait par faire bannir cette machine par son sshd (vécu 06/11/2026 : gen1 répondait « Not allowed at this time », l'empreinte devenait introuvable et le trust semblait ne jamais prendre) ; F5 / « Vérifier » force une passe complète. **Adresses de secours** : `check_host` essaie l'adresse principale puis les autres (LAN ↔ Tailscale) et renvoie celle qui a répondu (4e valeur), conservée dans `active` — un poste enregistré à la maison reste joignable par Tailscale en déplacement, sans intervention. L'état `penalty` distingue le blocage sshd d'un « injoignable » ordinaire. **Latence** = durée du handshake SSH complet : pas de connexion TCP nue en plus, sinon sshd verrait une sonde vide toutes les 30 s (et la compte dans ses pénalités). Tri en ligne d'abord, réordonné seulement en fin de passe ; rafraîchissement au retour de focus si le dernier date de > 8 s.
- **Copie de clé** : `ssh-copy-id` dans un vrai pty (session + `TIOCSCTTY`) pour que l'invite « password: » soit alimentée ; mot de passe jamais en argv ni enregistré, champ vidé après usage. Le probe `BatchMode` final fait foi, pas le code retour de ssh-copy-id. **Vérification préalable** (`KeyProbeWorker`) : le dialogue sonde d'abord si la clé est déjà acceptée et n'affiche le champ mot de passe qu'ensuite — un poste qui répond à la clé n'en demande aucun (titre « Clé déjà installée sur … », simple bouton Fermer) ; la sonde est bornée par les délais ssh (4 s) et Fermer reste désactivé pendant ce temps pour ne pas détruire le thread en vol. **L'ajout d'un poste inclut la copie** : `HostDialog` n'a plus qu'un bouton « Ajouter » (le mot de passe, facultatif, y est saisi une fois) et la fenêtre de clé démarre la copie **d'elle-même** quand ce mot de passe est fourni (`_initial_password` → `_start`, une seule fois) ; un import de plusieurs postes (mDNS, `~/.ssh/config`) passe par `_install_keys` : une sonde muette par poste (thread), clé marquée installée quand elle passe, et le dialogue ne s'ouvre que pour ceux qui la refusent encore, **un à la fois** (le suivant attend la fermeture du précédent). Rien n'est demandé sur un poste qui accepte déjà la clé. **Une connexion de sonde, réutilisée** : `key_status` rapporte dans la même connexion les clés d'hôte ET le fait que la clé est refusée ; ce pré-scan (`prescan`) est transmis au dialogue puis à `install_key`, et la sonde n'est rejouée ni avant `ssh-copy-id`, ni après un mot de passe refusé (la sortie de ssh-copy-id tranche). Compte tenu de `PerSourcePenalties` (5 s par échec, blocage à 15 s accumulées), une tentative ne doit pas dépasser **deux** connexions en échec : le scan, puis la copie. `ssh-copy-id` reçoit donc **`-f`** — sans lui il ouvre une connexion de test de plus (la clé est déjà connue comme refusée), ce qui atteignait le seuil et faisait bloquer la copie (vécu 06/11/2026).
- **Empreinte d'hôte** : une **seule connexion** ssh avec un `known_hosts` jetable (`scan_host_keys` : `StrictHostKeyChecking=no` + `UserKnownHostsFile` temporaire, `UpdateHostKeys=no`) rapporte les clés exactes — `ssh-keyscan` ouvrait une connexion par type de clé, chacune comptant comme offense pour `PerSourcePenalties`. Les empreintes SHA256 sont affichées, l'accord est explicite (bouton « Accepter l'empreinte »), puis **épinglage des clés exactes** dans `known_hosts` sous **toutes les adresses du poste** (LAN et Tailscale : même machine, même clé, donc changer d'adresse ne redemande pas la confiance) ; empreinte différente = refus (MITM), scan muet = refus (pas de trust à l'aveugle).
- **Actions distantes** : terminal (`konsole -e ssh`), arrêt / redémarrage (`systemctl poweroff|reboot`, code 255 « connection closed » = succès normal), et **les mêmes mises à jour que la machine courante** via le menu « Mettre à jour » de la carte : image Gablue (`sudo -n bootc upgrade` puis `bootc status`, `staged` → redémarrage requis), Flatpaks (même script qu'en local : `flatpak update --user -y` puis `sudo -n flatpak update --system -y`, donc sans mot de passe sur un poste Gablue, repli direct sinon), gwine (`gwine --init`, qui ne réinitialise le préfixe que si un composant a une nouvelle version) et Homebrew (même `brew update` + `brew upgrade` qu'en local, chemin absolu avec repli `command -v`, sans privilège). Journal en direct, annulable.
- **Options avancées à distance** : `RemoteSettingsDialog` lit l'état en **une seule connexion SSH** (`rpm-ostree kargs`, repli `cat /proc/cmdline`, plus la présence de `/etc/modules-load.d/gablue-cpuid-emu.conf`) et propose les mêmes quatre cases qu'en local, appliquées par les mêmes helpers (`sudo -n gablue-kargs`, `gablue-cpuid-emu`). **sudo à distance** : `remote_helpers_nopasswd()` sonde `sudo -n gablue-cpuid-emu status` (0 = règle NOPASSWD présente) ; sinon `QInputDialog` (écho masqué, jamais enregistré) puis `sudo -S -p '' -v` valide le cache une fois — le mot de passe part sur **stdin du ssh**, jamais dans argv — et le reste du script utilise `sudo -n`. Le chemin sert aussi au redémarrage et à l'extinction. `sudo -n true` ne sert PAS de sonde : aucune règle pour `true`, même sur Gablue ; `sudo -l` rend 0 dans tous les cas.
- **Redémarrage requis** (troisième pastille du pied de page, entre « Serveur SSH » et l'annonce mDNS) : visible seulement quand `local.pending_reboot_reasons()` rapporte quelque chose — image ostree `staged` (`rpm-ostree status --json`), kargs du prochain démarrage différents de `/proc/cmdline` (`BOOT_IMAGE=` écarté : il n'existe que côté noyau en cours, sinon tout poste semblerait en attente), configs écrites **après le démarrage** (`/etc/modprobe.d/wl-enable.conf`, `/etc/profile.d/vulkan-low-latency.sh` — une nouvelle session suffit pour celui-ci —, `/etc/modules-load.d/gablue-cpuid-emu.conf` et son blacklist — le test se nettoie tout seul au reboot suivant, aucune date figée, et une config livrée par l'image ne compte pas), et module `cpuid_fault_emulation` encore chargé alors que sa persistance a été retirée. Relu à chaque passe de 30 s dans `RebootWorker` (hors thread GUI, `rpm-ostree status` ~70 ms) : l'indication **survit à la fermeture de l'app**, rien n'est mémorisé côté session. Clic → confirmation listant les raisons → `privileged_prefix()` + `systemctl reboot` lancé détaché. Pas d'équivalent par poste distant : cela demanderait une connexion SSH par poste à chaque passe (la sonde de 30 s ne renvoie que l'état) ; piste = greffer la lecture sur la connexion existante ou la mettre en cache plusieurs minutes.
- **Découverte / import** : `avahi-browse -rtp _ssh._tcp` et parsing de `~/.ssh/config` `Include` compris (motifs `* ? !` ignorés), dans une liste à cocher **vide au départ** — rien n'entre dans le registre sans validation explicite (bouton « Ajouter (N) » désactivé tant que rien n'est coché, « Tout cocher » pour l'inverse) ; la découverte propose, elle n'ajoute pas. Les deux sont des entrées du menu du bouton **« Ajouter un poste »** (avec la saisie manuelle), pas des commandes séparées. **Une ligne par machine, pas par adresse** : Avahi annonce une adresse par interface du poste (boucle locale, `docker0`, `tailscale0`, LAN…), d'où quatre lignes pour un seul poste constaté le 05/11/2026. `hosts.group_candidates` écarte ce qui n'est pas joignable d'ici — boucle locale, `169.254/16`, **nos propres adresses** (une adresse identique à la nôtre est forcément l'interface du poste, pas la sienne), et toute adresse hors de nos sous-réseaux directs **sauf Tailscale** (`100.64.0.0/10`) — puis regroupe par nom mDNS + utilisateur + port et trie LAN avant Tailscale (l'adresse LAN est le défaut). L'interface locale est lue par `ip -o -4 addr show` (`hosts.parse_local_ipv4`, table vide = filtre permissif). Dans le dialogue, un poste à plusieurs adresses affiche une liste déroulante (« 192.168.1.109 (LAN) », « 100.64.0.45 (Tailscale) ») : c'est l'adresse choisie qui est enregistrée. Un poste déjà connu par **n'importe laquelle** de ses adresses (`hosts.known_targets` / `candidate_known`, toutes les adresses du registre, pas seulement la principale) **reste affiché** dans la liste avec le suffixe « déjà ajouté », grisé et non cochable : une seconde découverte qui retombait sur un poste connu affichait une liste vide, ce qui se lisait comme une panne (vécu 07/11/2026). Il n'est ni compté dans la sélection ni coché par « Tout cocher ». Les adresses non choisies ne sont plus jetées : elles deviennent les `addresses` de secours du registre.
- **Adresses du poste** (`hosts.remote_addresses`) : après une connexion réussie (installation de clé, ou premier état en ligne), le manager demande au poste son adresse LAN (`ip -4 route get 1.1.1.1`, donc pas `docker0`) et son adresse Tailscale (`tailscale ip -4`), puis les fusionne dans `addresses` (une fois par session et par poste, **tant qu'aucune adresse Tailscale n'est connue** — `util.has_address_kind`, sinon un poste ajouté en mDNS avec un secours LAN ne recevait jamais son adresse Tailscale). Le poste fait foi pour les types qu'il rapporte : une adresse Tailscale ou LAN périmée est **remplacée** au lieu de s'empiler (nœud réauthentifié, bail DHCP changé), seule l'adresse principale du registre n'est jamais retirée. C'est la seule façon de connaître l'adresse Tailscale d'un poste : Avahi n'annonce pas `tailscale0` de façon fiable — gen1 n'apparaissait qu'en LAN le 06/11/2026.
- **Serveur SSH local** : pastille au pied de page, `systemctl is-active`/`is-enabled`, bascule `sudo -n systemctl enable|disable sshd.service --now` (même effet que `ujust ssh-on/off`), **blanchi aux arguments exacts** dans `/etc/sudoers.d/nopasswd` (unité figée, pas de joker) donc sans mot de passe sur Gablue ; hors image, repli `pkexec` via `QProcess` (dialogue PolicyKit, bouton désactivé pendant l'attente) — jamais de `sudo` bloquant sur le thread GUI.
- **Annonce mDNS de ce poste** : seconde pastille du pied de page, lit la présence de `/etc/avahi/services/ssh.service` et l'état d'`avahi-daemon`. Activation et désactivation passent par `/usr/libexec/gablue-avahi on|off` (NOPASSWD, `status` pour la lecture) : il écrit lui-même le XML `_ssh._tcp` port 22 (`<name replace-wildcards="yes">%h</name>`, 0644, temporaire + `mv`) ou le retire. Un `sudo install` sur un fichier temporaire **ne pouvait pas** être blanchi aux arguments exacts (chemin aléatoire) et faisait donc ouvrir le dialogue PolicyKit à chaque bascule — vécu 06/11/2026. Avahi surveille le dossier et recharge seul (~1 s), aucun `systemctl restart`. Même schéma `sudo -n` → `pkexec`. **Pourquoi ce bouton** : le preset Fedora active bien `avahi-daemon`, mais `/usr/share/avahi/services/` est vide — sshd n'est donc jamais annoncé et la découverte de `gablue-manager` ne trouve rien sur un poste stock. L'annonce est **lien-local** (multicast `224.0.0.251:5353`, non routé) et ne publie que nom d'hôte, IP et port — aucun compte, aucune clé ; un poste qui s'y ferait passer pour un autre est bloqué par l'épinglage d'empreinte. Daemon arrêté → la pastille le dit et refuse la bascule (`sudo systemctl enable --now avahi-daemon`).
- **Bureau distant — relance sans erreur** : chaque clic ouvre une **nouvelle fenêtre**, même si une session tourne déjà (une seule session KRdp par utilisateur : le nouveau client coupe le précédent et sort en **2**, `STATE_RUN_QUIT`). Le code 2 est ignoré, comme le 131 de fermeture normale de `sdl-freerdp`, sinon un faux dialogue « La commande a échoué (code 2) » apparaissait à chaque reconnexion. Les sessions lancées par l'app restent suivies par poste (`host_id`, `kind="remote"`) : l'entrée **« Fermer la session de bureau distant »** du menu ⋯ n'est active que s'il y en a une, demande confirmation (défaut : non), puis envoie SIGTERM au groupe (SIGKILL après 3 s) pour que `gremote` nettoie tunnel SSH, serveur RDP et puits audio ; fermer la fenêtre à la main la désactive au poll suivant. Supprimer un poste ferme ses sessions.
- **Carte « Ce poste »** : fixe au-dessus de la liste (indépendante des postes enregistrés), nom d'hôte + utilisateur + `PRETTY_NAME` de `/etc/os-release`. Reprend les métriques des cartes de postes — hauteur 92, icône dans un emplacement de 26 px comme la pastille d'état, mêmes marges — sinon texte et boutons se décalent de 2 px d'une carte à l'autre ; tous les boutons ont la même hauteur (le style `accent` a le même rembourrage vertical que le style par défaut). Le bouton **« Configuration »** est un menu rangé par domaine, avec deux sous-menus : **Noyau et matériel…** (kargs + émulation CPUID) ; séparateur ; **Services et pilotes…**, **Variante de l'image…** ; séparateur ; **Jeux ▸ Options de gwine…, Priorité au premier plan…** et **Réseau ▸ Tailscale…** (chaque dialogue applique ses changements d'un coup) — le booster au premier plan est un réglage de jeu, il vit avec les options de gwine. Le menu ⋯ d'un poste distant reprend la même carte mentale dans un sous-menu **Réglages ▸** (Noyau et matériel, Jeux ▸ Options de gwine + Priorité au premier plan, Réseau ▸ Tailscale), au lieu de les semer au milieu des actions courantes. Menu **« Mettre à jour »** : image Gablue (`bootc upgrade`, appliquée au prochain démarrage), Flatpaks (`flatpak update --user -y` puis `sudo -n flatpak update --system -y` — la règle sudoers de l'image évite tout mot de passe ; hors image Gablue, repli sur l'appel direct et son dialogue PolicyKit), gwine (`gwine --init` : runner et composants DXVK/VKD3D, init seulement si un composant a changé) et Homebrew (`brew update` puis `brew upgrade`, même préfixe que les timers, `HOMEBREW_NO_AUTO_UPDATE=1` pour ne pas doubler l'update, aucun privilège). Le journal de `bootc upgrade` est traduit par `local.gablue_update_hint` (local et distant, seul le compte rendu d'upgrade compte, pas `bootc status`) : « déjà à jour » quand bootc répond « No changes in… », « rien de nouveau à télécharger, une image est déjà en attente » quand il ajoute « Staged update present, not changed » — chercher « staged » sans ce cas annonçait une nouvelle image après un no-op (vécu 07/11/2026) — et « redémarrage nécessaire » seulement sur « Queued for next boot »/« Upgraded ». La mise à jour **locale** affiche en plus une **barre de progression** alimentée par le JSONL de bootc (`--progress-fd`) et un bouton **« Terminal »** qui révèle le journal (masqué par défaut) : `/usr/libexec/gablue-update` (NOPASSWD, sans argument) crée `/run/gablue/update-progress.fifo` et y branche bootc, parce que sudo ferme les fd ≥ 3 ; l'app lit le FIFO sans privilège (`QSocketNotifier`, tâche `ProgressBytes`/`ProgressSteps` traduite par `local.parse_progress_event`, octets quand le total est connu, sinon étapes, sinon barre indéterminée). Repli sur `bootc upgrade` direct quand le helper manque (image antérieure) : bootc est alors muet, la fenêtre garde la même présentation avec une barre **indéterminée** (et dans « Tout mettre à jour… », une étape `busy` fait balayer la barre globale au lieu de la figer). La mise à jour **locale des Flatpaks** a le même traitement, sans helper : hors terminal flatpak écrit « Updating 3/7… » puis réémet la ligne avec un pourcentage (`local.parse_flatpak_progress`, msgid anglais non traduits en fr — vérifié 07/11/2026, flatpak 1.18.4), `LocalTaskDialog(progress_parser=local.parse_flatpak_progress)` en tire une barre globale à la phase — `(op-1 + pct/100)/total` — et masque le journal derrière le même bouton **« Terminal »** ; les compteurs repartent à zéro entre les deux phases (compte puis système), la barre redescend donc une fois. `local.flatpak_update_hint` ne conclut « Aucune mise à jour disponible. » que si aucune opération n'a démarré (la phase système dit presque toujours « Nothing to do. »). **Homebrew n'a pas d'équivalent en pourcentage** : hors terminal `curl` est lancé en `--silent` (`utils/curl.rb`, Homebrew 7.0.12 vérifié 07/11/2026), donc aucune jauge ni débit, et la file de téléchargements concurrente ne rend que des lignes de fin. `local.brew_progress_parser()` (analyseur stateful, un par fenêtre) donne donc une barre **par formule** : `Fetching downloads for: a, b` fournit la liste (donc le total, Homebrew 7 ne résumant qu'après) avec une barre indéterminée faute de pourcentage, puis chaque `Upgrading <nom>` avance d'un cran — les lignes `… dependency: <dep>` ne comptent pas ; `local.brew_update_hint` dit « Aucune formule à mettre à jour. » quand `brew upgrade` n'écrit rien. **« Tout mettre à jour… »** (en tête du menu) enchaîne les étapes **disponibles** dans une seule fenêtre `tasks.SequentialTaskDialog` : image Gablue (helper/FIFO ou `bootc upgrade`), Flatpaks, gwine puis Homebrew, chacune gardant son analyseur ; la barre **globale** vaut `(étapes terminées + fraction courante) / total`, un outil absent est omis (pas une erreur), et un échec arrête la suite en laissant la fenêtre et le journal ouverts (barre plancher aux étapes accomplies). Quand aucun pourcentage n'est disponible (téléchargements de brew, bootc sans total, attente avant le premier événement), la barre bascule sur **`widgets.BusyProgressBar`** : un segment peint qui balaie la piste de gauche à droite, parce qu'un `QProgressBar` en mode indéterminé (`range(0,0)`) ne s'anime pas sous feuille de style Qt ; le mode déterminé est habillé par le QSS (`#taskProgress` : même piste arrondie, chunk accent, pourcentage centré), le timer s'arrête barre masquée, et la bande d'activité de 3 px de l'en-tête utilise le même widget. Chaque action est confirmée puis suivie dans `LocalTaskDialog` (QProcess, canaux fusionnés, annulation par `setsid`, codes 125/126/127 traduits).
- **Applications** (bouton « Applications » de la carte « Ce poste » et entrée « Applications… » du menu ⋯ d'un poste) : dialogue **non modal** en deux sections, « Émulateurs » (ES-DE, Azahar, Eden, Xenia, ShadPS4) et « Outils » (OpenCode 2), avec pour chaque ligne l'état (AppImage `~/AppImages`, version GearLever, version CLI quand il y en a une), un bouton **Installer/Mettre à jour** et **Supprimer**. **Local et distant** partagent le même dialogue (`host=None` ou un poste) : à distance l'état est lu en **une seule connexion SSH** (`REMOTE_STATE_SCRIPT` : GearLever, `ls ~/AppImages`, `opencode --version`, chemins des scripts + options qu'ils connaissent, découpé par `parse_remote_state`/`remote_states`) et les actions passent par `RemoteTaskDialog`, jamais par un `exec()` ; poste injoignable → lignes « État indisponible » et boutons désactivés. Aucune logique de téléchargement n'est réimplémentée : le manager lance le script existant de l'image (`esde-install`, `azahar-install`, `eden-install`, `xenia-install`, `shadps4-install`, `opencode2-install`) et affiche son journal ; ES-DE reçoit `--yes` (le journal remplace ses boîtes kdialog) et expose en plus **« Mettre à jour la config »** (`--config-only` : `custom_systems` + lanceurs Tools, sans toucher à l'AppImage). **Le manager lit le script pour savoir ce qu'il accepte** (`script_has_option`, jamais en l'exécutant ; à distance, `grep` dans la sonde) : un `esde-install` plus ancien que le paquet ignore les arguments inconnus et lancerait l'installation interactive (« ES-DE semble déjà installé… », constaté) — en local le manager fait alors la copie lui-même (`copy_esde_config`, même règle : `~/ES-DE/custom_systems`, `<ROMDirectory>/tools/`, lanceur existant non écrasé), à distance il refuse avec un message « mettre à jour l'image du poste » (la copie ne peut pas être faite à moitié à travers SSH). La suppression est générique (retrait GearLever, AppImage, `.desktop`, icônes) sauf OpenCode 2, qui passe par `opencode2-remove` (CLI npm, symlink, entrées Dolphin + `mimeapps.list`, MCP Lightpanda) : **configuration, sauvegardes, jeux et sessions ne sont jamais touchés** (`~/ES-DE`, `~/Roms`, `~/.config/opencode`, `~/.config/ai.opencode.desktop`, `~/.local/share/opencode`). Supprimer OpenCode 2 arrête son serveur de fond — donc les sessions ouvertes sur ce poste (y compris une session lancée par SSH) ; `opencode2-remove` absent du poste → suppression désactivée (pas de retrait à moitié). GearLever absent → installation/mise à jour désactivées, suppression toujours possible ; script absent de l'image → bouton désactivé avec l'explication en infobulle. Les six cartes défilent (`QScrollArea`) pour tenir sur un écran 800 px.
- **Noyau et matériel** (`Noyau et matériel…`, ex-« Réglages du noyau », local et distant) : dialogue d'`dialogs/kernel.py` à **cinq cases à cocher** — protections contre les failles du processeur (`mitigations=off`), correctif CPUID pour certains jeux (`clearcpuid=514`, ex-`ujust cpuid-fix-on/off`), mode ERTM du Bluetooth (`bluetooth.disable_ertm=1`), **HDMI 2.1 sur GPU AMD** (`amdgpu.dcfeaturemask=0x402`, ex-`ujust configure-amd-hdmi21`) et émulation CPUID fault (`cpuid_fault_emulation`, ex-`ujust cpuid-emu-on/off`) — avec un seul bouton **« Appliquer »**, actif seulement si une case diffère de l'état du poste. Les **quatre** kargs partent en **un unique** appel à `/usr/libexec/gablue-kargs` (un déploiement), l'émulation CPUID dans `/usr/libexec/gablue-cpuid-emu on|off` (elle charge un module et occupe SVM, donc KVM) ; fermer avec des cases modifiées demande confirmation. Les deux helpers sont en NOPASSWD : **aucune invite de mot de passe** sur un poste Gablue. Les **cinq** cartes portent une **pastille de conseil** (`recommendation_badge`/`set_recommendation`, `uiutil`) : **l'état conseillé** en vert quand le choix courant le suit (« ✓ Conseillé : activé|désactivé », repris de `CHOICE_STATE`), **le geste** en orange quand il s'en écarte (« Conseillé : à activer|à désactiver », « choisir X11 ») — **le texte dit l'écart**, la couleur ne fait que le renforcer (une couleur seule se lisait mal). Un « ✓ Conseillé » nu, posé à côté d'une case décochée, se lisait comme « il est conseillé de cocher » : le vert nomme donc toujours la valeur. Elle disparaît tant que l'état est illisible. Conseil par case : protections activées, **correctif CPUID activé** (débloque des jeux sans coût ailleurs), ERTM désactivé, HDMI 2.1 désactivé (FreeSync et fonctions 2.1, mais scintillements possibles sur certains écrans : opt-in explicite), émulation CPUID fault désactivée. **L'état lu est celui du prochain démarrage** (`rpm-ostree kargs`, sans root), pas `/proc/cmdline` qui décrit le noyau en cours — sinon les cases reviendraient à l'ancienne valeur juste après l'application ; l'émulation est lue dans `/etc/modules-load.d/gablue-cpuid-emu.conf`. Les kargs ne prennent effet qu'au redémarrage, le dialogue le dit.
- **Services et pilotes** (`Services et pilotes…` du menu **Configuration** de la carte « Ce poste ») : dialogue local d'`dialogs/services.py`, ex-recettes ujust. **Six cases** — DisplayLink (service), Docker, couche Vulkan low-latency, pilote Wi-Fi Broadcom `wl`, historique atuin, mises à jour automatiques — avec un seul **« Appliquer »** et la valeur recommandée affichée (low-latency, atuin et mises à jour automatiques activés). **DisplayLink, Docker et le Wi-Fi Broadcom n'ont pas de recommandation** : les deux premiers dépendent du matériel du poste, Docker n'est qu'un service désactivé par défaut — une pastille y dirait « décochez » à qui a justement le dock ou la carte, et la case reflète simplement l'état réel. **Docker n'est affiché que sur une variante DX** (`docker_available(variant)`, suffixe `-dx`) : ailleurs le paquet n'existe pas. **Mises à jour automatiques** = timers `rpm-ostreed-automatic.timer` + `flatpak-system-update.timer` + `brew-update.timer` + `brew-upgrade.timer` (image Gablue, Flatpaks système et Homebrew) basculés par `/usr/libexec/gablue-auto-update on|off` (sudo -n), plus `flatpak-user-update.timer` en `systemctl --user` (sans privilège, best-effort : message si aucune session) ; l'état est lu par le helper en `status` et la session par `systemctl --user is-enabled`, les deux moitiés devant être actives pour afficher « activées ». Périmètre de `ujust toggle-updates-all` (upstream `toggle-updates` laisse brew de côté) : sans les timers brew, décocher la case les laissait tourner chaque samedi et l'affichage mentait ; la ligne disparaît si le helper n'est pas dans l'image (`auto_update_available`). L'état des autres cases vient de `systemctl is-enabled`, de la présence de `/etc/profile.d/vulkan-low-latency.sh` et de `/etc/modprobe.d/wl-enable.conf`, et de `atuin init bash` dans `~/.bashrc` ; l'application passe par `/usr/libexec/gablue-service`, `gablue-low-latency` et `gablue-broadcom-wl` (sudo -n) puis `/usr/bin/gablue-atuin` (sans privilège, fichiers de l'utilisateur) — un seul script, une seule tâche. **Atuin** : `on` installe ble.sh et branche un bloc balisé dans `~/.bashrc` (les lignes héritées d'ujust sont fondues dedans, jamais dupliquées) — l'`eval` porte **`--disable-up-arrow`** pour que la flèche Haut reste à ble.sh (historique du shell) et qu'atuin ne s'ouvre que par Ctrl-R, configuration du poste de référence (05/11/2026) ; `off` retire le bloc et ble.sh, avec instantané `~/.bashrc.gablue-atuin.bak`, mais **ne touche jamais** `~/.local/share/atuin` (historique) ni `~/.config/atuin`. Si les helpers ne sont pas dans l'image, les cases sont désactivées avec « reconstruction requise » plutôt que de lancer des commandes absentes. La **variante d'image** a son propre dialogue (`dialogs/variant.py`) : un rebase est un geste lourd et destructeur, il ne cohabite plus avec des bascules réversibles.
- **Variante de l'image** (`Variante de l'image…` du menu **Configuration**, dialogue d'`dialogs/variant.py`) : liste `REBASE_VARIANTS` (main, main-dx, nvidia, nvidia-open, nvidia-open-dx), libellé « variante actuelle » / « variante inconnue », et bouton **« Basculer »** actif seulement si la variante choisie diffère de `local_variant()` (`rpm-ostree status --json`, déploiement `booted`, `gablue-<variante>` dans la référence d'image) ; confirmation explicite, téléchargement de l'image, effet au redémarrage. Helper `gablue-rebase` absent de l'image → bouton désactivé avec « helper absent — reconstruction requise » (`rebase_helper_available`).
- **Options de gwine** (`Options de gwine…`, local et distant) : lit `~/.local/share/gwine/options` (`dxvk_mode`, `display_mode`, `xbox_default`, SSH pour un poste distant) et applique par gwine lui-même — `gwine --dxvk-async|--dxvk`, `gwine --wayland|--x11`, `gwine --xbox-on|--xbox-off` (tout ou rien ; le filtre `--xbox-ds4`/`--xbox-dualsense` reste en CLI) : le fichier garde son format et le préfixe reçoit les DLL DXVK correspondantes. Conseil affiché sur les trois réglages : DXVK standard (pas d'async), X11 plutôt que Wayland natif, Xbox 360 désactivé. Effet au prochain lancement de jeu, aucun privilège, journal en direct.
- **Priorité au premier plan** (`Priorité au premier plan…`, local et distant) : ex-`ujust foreground-booster-enable/disable`, refait sans passer par ujust — `kwriteconfig6 --file kcgroupsrc --group 'Foreground Booster' --key autostart true|false` puis `systemctl --user restart|stop plasma-foreground-booster.service` (best-effort : à distance sans bus de session, le fichier reste ce qui compte à la prochaine connexion). Recommandé : activé.
- **Tailscale** (`Tailscale…`, local et distant) : case activée/désactivée, état lu en une seule commande (`systemctl is-enabled|is-active tailscaled`, `tailscale debug prefs` pour le serveur). À l'activation, le lien du **serveur de connexion** est demandé (`QInputDialog`, prérempli avec le serveur déjà configuré) et validé (`http://` ou `https://`, sans espace ni guillemet) : contrairement à `ujust tailscale-up`, aucun serveur n'est codé en dur. Application par `/usr/libexec/gablue-tailscale on --login-server URL|off` (NOPASSWD) : `tailscale up --operator=$SUDO_USER`, service + firewall en `on`, arrêt + désactivation en `off`. **Aucune pastille de conseil** : Tailscale est un opt-in (on l'utilise ou pas), il n'y a pas de « bon » réglage à recommander.
- **Barres des configurations** : les fenêtres de réglages (noyau, services, variante, options gwine, booster, Tailscale — **locales et distantes**) adoptent la présentation des mises à jour : barre de progression, journal **masqué** derrière « Terminal », révélé automatiquement en cas d'échec. Le mode est explicite (`progress_mode="busy"` pour une barre indéterminée, `progress_parser` quand la commande publie des étapes) : les **kargs** restent **non progressifs** (un seul déploiement rpm-ostree, aucune progression mesurable) ; **Services et pilotes** a une vraie barre par domaine, `local.system_apply_script` émettant `::gablue:step n total libellé` (total = domaines réellement modifiés) et `::gablue:done` ; variante = indéterminée (téléchargement rpm-ostree muet). `tasks._display_command` résume un script `bash -c` multi-ligne en `<script>` dans l'en-tête du journal, au lieu d'y déverser le script et ses lignes de protocole.
- **Enregistrement Tailscale** : `tailscale up` lancé en root n'ouvre pas de navigateur — il écrit le lien d'authentification sur sa sortie. `local.find_auth_url` retient le **dernier** lien de la sortie en écartant le serveur de connexion (le chemin varie : Tailscale `/a/…`, headscale `/register/…`), `tasks._AuthLinkRow` l'affiche dans la fenêtre (cliquable, bouton **« Copier le lien »**), et `local.tailscale_registered` (sonde `tailscale status --json`, toutes les 1,5 s) constate `BackendState == "Running"` : le lien disparaît alors et le libellé passe à « Appareil enregistré. ». « Annuler » coupe `tailscale up` (SIGTERM puis SIGKILL) et masque le lien. À distance, le lien est extrait de la sortie SSH (pas de sonde) et masqué à la fin.
- **Opérations simultanées** (`start_task`) : chaque opération (mise à jour, redémarrage, réglages, copie de clé) est une fenêtre **non modale** rattachée à la fenêtre principale — plusieurs postes peuvent être traités en même temps, et la fenêtre principale reste utilisable. Les dialogues de configuration se ferment après « Appliquer » et laissent la tâche tourner ; `_tasks` garde les fenêtres vivantes, `completed` déclenche le rafraîchissement des cartes. Un `exec()` (modale) ne doit plus servir qu'aux dialogues qui rendent un résultat immédiat (ajout/édition de poste, choix de candidats).
- **Privilèges** : `privileged_prefix()` sonde `sudo -n /usr/libexec/gablue-cpuid-emu status` (0 = règle NOPASSWD présente) puis retombe sur `pkexec` (dialogue PolicyKit) — `sudo -n true` échouait toujours, même sur Gablue, et faisait passer toute action root par PolicyKit malgré la règle sudoers. **Même piège à distance** : `remote_sudo_nopasswd()` sonde `sudo -n gablue-cpuid-emu status`, seul helper dont `status` sort 0 quelle que soit la configuration ; `sudo -n true` n'a aucune règle, et `gablue-auto-update status` sort 1 dès qu'un timer est désactivé — un poste aux mises à jour coupées passait pour « sans règle NOPASSWD » et réclamait le mot de passe pour redémarrer, éteindre ou faire `bootc upgrade` pourtant autorisé. Les réglages noyau, émulation CPUID, services, couche Vulkan, pilote Wi-Fi, mises à jour automatiques, rebase et Tailscale n'utilisent ni l'un ni l'autre : ils passent par les helpers `/usr/libexec` en `sudo -n` (sans invite). Serveur SSH et annonce mDNS ont leurs règles exactes (systemctl sshd, `gablue-avahi`), redémarrage/extinction distants aussi (`systemctl reboot|poweroff`). Aucune commande root n'est lancée sur le thread GUI.
- **Actions externes** : `gremote [-p port] user@host` (port non standard) et `dolphin sftp://user@host:port/` (IPv6 entre crochets). Lancement détaché (`start_new_session`) : fermer la fenêtre ne tue pas la session RDP ; sortie capturée et affichée seulement si le code retour est ≠ 0, sauf le 131 de `sdl-freerdp` (fermeture normale de la fenêtre RDP) et les arrêts demandés depuis l'app.
