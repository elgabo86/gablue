# Gablue Manager — paquet `gablue_manager` (src/gablue-manager)

GUI PySide6 (Wayland natif) : liste des postes SSH avec état et latence, bureau distant (`gremote`), fichiers (`dolphin sftp://`), terminal SSH, arrêt / redémarrage / mise à jour des postes, recherche sur le réseau local, ajout + copie de clé — **et la machine courante** : serveur SSH, annonce locale, mises à jour (image Gablue, Flatpaks, gwine, Homebrew) et options avancées (ex-`gablue-config`), services et variante de l'image (ex-recettes ujust). Nom affiché « Gablue Manager » ; binaire et `.desktop` = `gablue-manager` / `gablue-manager.desktop` (convention `gablue-*`), **catégorie Système** (`Categories=System;`) et icône maison `gablue-manager` (`/usr/share/icons/hicolor/scalable/apps/gablue-manager.svg` : carré bleu Gablue, anneau en **engrenage à 8 dents** formant un G — ouverture en haut à droite et barre horizontale, le tout en une seule silhouette), avec repli `network-server` hors image via `uiutil.app_icon()`. Remplace l'ancien `gablue-ssh`, `/usr/libexec/gablue-config` (script kdialog supprimé, ainsi que `gablueconfig.desktop` et son entrée de blacklist) et `gablue-update` (script Python et `gablueupdate.desktop` supprimés, ainsi que son entrée de blacklist, la recette `ujust gablue-update`, l'alias `gablue-update` et la ligne d'aide correspondante) : les mises à jour se lancent depuis la carte du poste.

**Onglets** : **deux seulement, centrés** — `<nom d'hôte> (local)` et « Postes SSH » (position fixe 1). Aucun onglet par poste distant : un **simple clic** sur une carte (fond, nom ou ligne d'état, `open_host_tab`) affiche sa page **dans « Postes SSH »**, par-dessus la liste (`QStackedWidget` : liste, page vide, puis une page par poste construite à la demande) ; la rangée d'outils et le panneau « Accès à ce poste » de la liste disparaissent alors. On revient à la liste par la **croix ✕ au-dessus de la carte** (`show_hosts_list`) ou en cliquant le titre **« Postes SSH »** quand il est déjà courant (filtre d'événements sur la barre d'onglets : `QTabWidget` n'émet rien dans ce cas) ; arriver sur l'onglet montre toujours la liste. Le centrage passe par `widgets.CenteredTabs` : la barre native est masquée et remplacée par un en-tête maison (boutons `#tabButton` centrés, `QButtonGroup` exclusif), parce que `SH_TabBar_Alignment` est ignoré dès qu'un QSS est appliqué et qu'un `QProxyStyle` sur la barre **fait planter Qt à la fermeture** (segfault constaté 07/11/2026). `CenteredTabs` garde l'API de `QTabWidget` (`addTab`, `setTabText`, `setCurrentIndex`, `currentChanged`) et ajoute `reclicked` pour le clic sur l'onglet déjà courant. Le mode document est désactivé (sa ligne de base pleine largeur flotte au-dessus d'onglets centrés). L'état d'un poste distant n'est sondé que sur **sa page** (`refresh_all` ← `_tab_changed`/`_current_pane_host`) ou sur la liste « Postes SSH » ; le poste local est relu à chaque passe, et le résumé matériel d'un poste distant n'est chargé qu'à l'ouverture de sa page (une connexion SSH, cache de session).
- **Fermeture** : `closeEvent` demande l'arrêt de toutes les sondes de fond (annulation coopérative : `stop()`, `threading.Event`, `cancel`) puis attend avec un **budget global de 3 s** — jamais `terminate()`, un `pthread_cancel` sur un thread Python fait tomber le processus (vécu 07/11/2026). Si une sonde résiste, `has_running_workers()` est vrai et `app.main` sort par `os._exit` : le processus s'arrête avec la fenêtre, au lieu d'attendre la fin d'un `brew update` de deux minutes. `updates.cancel_running()` tue les commandes externes en cours (registre de `Popen` dans `updates._run`), et `apps.pending_updates(stop=…)` cesse d'attendre les flux restants.

Sources = ce dossier (`src/gablue-manager/`), installées par
`files/scripts/build-manager` :

| `gablue_manager/instance.py` | instance unique fenêtre/tray (socket locale), lancement de la fenêtre |

| `gablue_manager/local.py` | état/commandes de la machine (sshd, avahi, kargs, CPUID, services, variante, atuin, gwine, booster, Tailscale) |

| `gablue_manager/remote_updates.py` | mises à jour d'un **poste distant**, à la demande : script SSH balisé, analyse (`parse_check`, domaine applications compris), chaîne « tout mettre à jour » (`update_chain(pending, states)`, section `apps_section`) |
| `gablue_manager/remote_hardware.py` | résumé matériel d'un **poste distant** en une connexion SSH (script balisé `::gablue:*`, analyse réutilisant `local`) |

| `gablue_manager/widgets.py` | `BusyProgressBar`, `StatusDot`, `HostCard`, `LocalConfigMenu`, `InfoPanel`, `UpdatesPanel`, `AccessPanel`, `NoticeBar` |
| `gablue_manager/dialogs/` | un fichier par dialogue (`host`, `key`, `kernel`, `grub`, `secureboot`, `services`, `variant`, `btrfs`, `thermal`, `ryzen`, `clean`, `stversions`, `gwine`, `booster`, `tailscale`, `apps`, `updates`, `prefs`) |
| `gablue_manager/window.py` | `MainWindow` |
| `tests/` | tests unitaires stdlib des fonctions pures |

**Règle** : le paquet est la source de vérité ; ne pas réintroduire de fichier
unique assemblé. Un nouveau dialogue → un fichier dans `dialogs/` + une entrée
de menu dans `window.py`. Les imports relatifs vont dans un seul sens
(`constants ← util ← hosts/ssh/local ← workers/tasks ← dialogs ← window ← app`) :
un cycle (ex. `_ssh_opts` entre `hosts` et `ssh`) se règle en descendant la
fonction dans le module le plus bas, pas par un import tardif.

## Build

- `Containerfile-gablue` : `COPY src/gablue-manager /src/gablue-manager`, puis
  `RUN /ctx/build-manager` juste après `build-gwine`.
- `files/scripts/build-manager` : copie `gablue_manager/` dans
  `/usr/lib/gablue-manager/`, installe le lanceur en `/usr/bin/gablue-manager`
  (755) et retire les `__pycache__` (le Python du build n'est pas celui du
  poste, `/usr` est en lecture seule sur composefs).
- Développement : `src/gablue-manager/gablue-manager --help` marche depuis le
  dépôt ; `PYTHONPATH=src/gablue-manager python3 -c "import gablue_manager.app"`.
- L'image doit être reconstruite pour valider l'installation (pas l'ISO).

## Modes CLI (sans fenêtre principale)

`gablue-manager` sans argument ouvre la fenêtre principale. Trois modes
n'instancient **que** la boîte demandée : `MainWindow` n'est jamais créée, donc
aucune sonde SSH (les `CheckWorker` du timer de 30 s), aucun scan Avahi, aucun
accès au registre des postes.

| Mode | Rôle |
|---|---|
| `--progress --title T [--subtitle T] [--auto-close-success\|--auto-close] -- commande…` | `LocalTaskDialog` sur la commande (canaux fusionnés, annulation SIGTERM puis SIGKILL). La commande publie `::gablue:step n total texte`, `::gablue:busy texte` (total inconnu) et `::gablue:done [texte]` ; ces lignes de protocole sont retirées du journal (`local.parse_gablue_progress`), l'outil écrivant sa version lisible à côté. Échec → journal révélé ; `--auto-close-success` ferme la fenêtre en cas de succès. Code de sortie = celui de la commande (130 si annulé). |
| `--confirm --title T --text T [--yes T] [--no T]` | `QMessageBox` ; sortie 0 = oui, 1 = non. |
| `--choose --title T --text T --item valeur [--item valeur…]` | `QInputDialog` ; imprime la valeur choisie (libellé après une tabulation), sortie 1 si annulé. |

Sans affichage, `--progress` exécute la commande telle quelle (sans protocole)
et `--confirm` répond non : gwine reste utilisable en terminal. gwine s'en sert
au premier lancement (initialisation du préfixe dans la fenêtre de progression),
dans `conflict.sh`/`wgp/mount.sh` (oui/non) et `wgp/modes.sh` (choix de
l'exécutable d'un WGP). Les mises à jour locales de gwine dans la fenêtre
principale passent aussi `GABLUE_PROGRESS=1` et `parse_gablue_progress`, donc
la barre d'étapes remplace le journal, resté derrière « Terminal ».

## Comportement

- **Registre** `~/.config/gablue/ssh-hosts.json` (dossier 0700, fichier 0600, écriture atomique `mkstemp` + `os.replace`) : source de vérité de l'app. Un poste ajouté uniquement par `ssh-key-add` en CLI n'y figure pas (le script ne consigne rien) — il s'ajoute à la main. Registre illisible → renommé `ssh-hosts.corrupt-<horodatage>.json`, jamais écrasé. Champs `addresses` (adresses de secours de la même machine : LAN, Tailscale) et `active` (celle qui a répondu en dernier, utilisée par `ssh_target`/`dolphin_url`) ; l'ancien champ `mac` (Wake-on-LAN, fonction retirée le 06/11/2026) est ignoré et disparaît au premier enregistrement.
- **État** : `ssh -i ~/.ssh/id_ed25519 -o IdentitiesOnly=yes -o BatchMode=yes -o StrictHostKeyChecking=yes -p N … true`, 6 postes en parallèle, relance toutes les 30 s, test annulable à la fermeture. `BatchMode` + `IdentitiesOnly` = c'est bien NOTRE clé qui est testée ; pas d'`accept-new` ici, un simple ping ne doit pas écrire dans `known_hosts`. Vert = clé acceptée, orange = joignable mais clé refusée, violet = empreinte d'hôte inconnue, gris = hors ligne / DNS. **Pas de sonde répétée des états bloqués** (`NO_AUTO_PROBE_STATES` : `auth`, `hostkey`, `penalty`) : une connexion qui se ferme avant authentification compte comme offense pour `PerSourcePenalties` (OpenSSH 9.8+ — `authfail` 5 s, blocage dès 15 s accumulées, jusqu'à 10 min), et sonder toutes les 30 s un poste qui refuse la clé finissait par faire bannir cette machine par son sshd (vécu 06/11/2026 : gen1 répondait « Not allowed at this time », l'empreinte devenait introuvable et le trust semblait ne jamais prendre) ; F5 / « Vérifier » force une passe complète. **Adresses de secours** : `check_host` essaie l'adresse principale puis les autres (LAN ↔ Tailscale) et renvoie celle qui a répondu (4e valeur), conservée dans `active` — un poste enregistré à la maison reste joignable par Tailscale en déplacement, sans intervention. L'état `penalty` distingue le blocage sshd d'un « injoignable » ordinaire. **Latence** = durée du handshake SSH complet : pas de connexion TCP nue en plus, sinon sshd verrait une sonde vide toutes les 30 s (et la compte dans ses pénalités). Tri en ligne d'abord, réordonné seulement en fin de passe ; rafraîchissement au retour de focus si le dernier date de > 8 s.
- **Copie de clé** : `ssh-copy-id` dans un vrai pty (session + `TIOCSCTTY`) pour que l'invite « password: » soit alimentée ; mot de passe jamais en argv ni enregistré, champ vidé après usage. Le probe `BatchMode` final fait foi, pas le code retour de ssh-copy-id. **Vérification préalable** (`KeyProbeWorker`) : le dialogue sonde d'abord si la clé est déjà acceptée et n'affiche le champ mot de passe qu'ensuite — un poste dont la clé **et** l'empreinte sont déjà connues n'en demande aucun (titre « Clé déjà installée sur … », simple bouton Fermer) ; la sonde est bornée par les délais ssh (4 s) et Fermer reste désactivé pendant ce temps pour ne pas détruire le thread en vol. **L'ajout d'un poste inclut la copie et n'a lieu qu'après vérification** : `HostDialog` n'a qu'un bouton « Ajouter » (le mot de passe, facultatif, y est saisi une fois) ; le poste n'entre dans `_hosts`, `ssh-hosts.json` et la liste **qu'une fois `ssh.key_ready` vrai** (clé acceptée ET empreinte épinglée) — sinon il est écarté et une boîte « Postes non ajoutés » dit lesquels et pourquoi. Un ajout de plusieurs postes (recherche sur le réseau local) passe par `_install_keys` : une sonde muette par poste (thread), et le dialogue ne s'ouvre que pour ceux qui la refusent encore, **un à la fois** (le suivant attend la fermeture du précédent). **Aucun bouton « Installer la clé »** : le dialogue demande le mot de passe quand il en faut un (Entrée lance la copie) et démarre seul l'épinglage quand la clé est déjà acceptée. Le succès exige l'empreinte : `authenticated` seul ne suffit pas, le pré-scan travaillant sur un `known_hosts` jetable — il laissait ajouter un poste « clé installée » sans épingler l'empreinte, d'où une carte « Clé d'hôte inconnue » sans jamais de question de trust (vécu 08/11/2026, sucina). **Une connexion de sonde, réutilisée** : `key_status` rapporte dans la même connexion les clés d'hôte ET le fait que la clé est refusée ; ce pré-scan (`prescan`) est transmis au dialogue puis à `install_key`, et la sonde n'est rejouée ni avant `ssh-copy-id`, ni après un mot de passe refusé (la sortie de ssh-copy-id tranche). Compte tenu de `PerSourcePenalties` (5 s par échec, blocage à 15 s accumulées), une tentative ne doit pas dépasser **deux** connexions en échec : le scan, puis la copie. `ssh-copy-id` reçoit donc **`-f`** — sans lui il ouvre une connexion de test de plus (la clé est déjà connue comme refusée), ce qui atteignait le seuil et faisait bloquer la copie (vécu 06/11/2026).
- **Empreinte d'hôte** : une **seule connexion** ssh avec un `known_hosts` jetable (`scan_host_keys` : `StrictHostKeyChecking=no` + `UserKnownHostsFile` temporaire, `UpdateHostKeys=no`) rapporte les clés exactes — `ssh-keyscan` ouvrait une connexion par type de clé, chacune comptant comme offense pour `PerSourcePenalties`. Les empreintes SHA256 sont affichées, l'accord est explicite (bouton « Accepter l'empreinte »), puis **épinglage des clés exactes** dans `known_hosts` sous **toutes les adresses du poste** (LAN et Tailscale : même machine, même clé, donc changer d'adresse ne redemande pas la confiance) ; empreinte différente = refus (MITM), scan muet = refus (pas de trust à l'aveugle).
- **Actions distantes** : terminal (`konsole -e ssh`), arrêt / redémarrage (`systemctl poweroff|reboot`, code 255 « connection closed » = succès normal), et **les mêmes mises à jour que la machine courante** via le bouton « Mettre à jour » de la carte distante — **premier bouton de la rangée, avant « Bureau distant »** ; fichiers et terminal passent en icônes compactes (`_make_tool_button`) parce que cinq libellés ne tenaient plus ; son menu : vérification à la demande, « Tout mettre à jour… », puis image Gablue, Flatpaks, gwine, **applications** et Homebrew : « Tout mettre à jour… » lance `remote_updates.update_chain(pending, states)` sur ce seul poste — la liste des AppImages en retard vient de `probe_apps` (une connexion SSH pour l'état + les flux de releases lus **d'ici**), donc la sonde part d'abord et la confirmation nomme les applications concernées, l'étape étant omise quand tout est à jour ; image Gablue (`sudo -n bootc upgrade` puis `bootc status`, `staged` → redémarrage requis), Flatpaks (même script qu'en local, `sudo -n flatpak update --system -y` : Gablue n'installe qu'en système, aucun `--user` ; sans mot de passe sur un poste Gablue, repli direct sinon), gwine (`gwine --init`, qui ne réinitialise le préfixe que si un composant a une nouvelle version), applications (`apps_section` : la commande du poste, lue par `apps.remote_states` — chemin du script et options qu'il connaît ; une application dont le script manque ou ne connaît pas `--yes` est **ignorée avec un message** dans le journal, jamais lancée en interactif où elle attendrait ses boîtes kdialog) et Homebrew (même `brew update` + `brew upgrade` qu'en local, chemin absolu avec repli `command -v`, sans privilège). Journal en direct, annulable. **Vérification uniquement à la demande** (`remote_updates.check`, `workers.RemoteUpdatesWorker`) : une connexion SSH, sections `::gablue:*` analysées par `parse_check` (même format que le poste local) plus l'état des AppImages (`::gablue:apps` puis les sections `##nom` de `apps.REMOTE_STATE_SCRIPT` : sans ce marqueur, les `##` atterrissent dans la section gwine et faussent son analyse), le domaine « applications » étant calculé après la connexion par `updates.apps_domain(*apps.pending_for(...))` — les flux se lisent d'ici, le poste n'a besoin d'aucun accès réseau sortant ; résultat affiché sur la carte (compteur du bouton, ligne d'état « N mises à jour », infobulle et comptes du menu) ; aucune sonde périodique ne part sur le réseau, et une action distante réussie oublie le compteur connu (`_remote_after_task`) au lieu de l'afficher périmé.
- **Lot sur les postes en ligne** (section « Postes en ligne » du bouton **« Mises à jour »** de l'en-tête, `tasks.RemoteBatchDialog`) : « Vérifier les mises à jour » sonde **tous les postes en ligne** (trois connexions à la fois, résultat affiché sur chaque carte) ; « Tout mettre à jour… » lance sur chaque poste **en parallèle**, trois ssh à la fois, dans **une seule fenêtre**, la chaîne de ce poste : `remote_updates.update_chain(pending, states)` (image, Flatpaks `--system`, gwine, applications, Homebrew), chaque poste recevant la sienne par `RemoteBatchDialog(commands=…)` — une `RemoteAppsWorker` par poste (état par SSH, flux de releases lus d'ici) précède le lancement, jamais une commande unique supposée bonne pour tous ; une ligne par poste (En attente / En cours / Terminé / Échec + code), barre globale, journal commun derrière « Journal » (préfixé du nom du poste), annulation qui tue les ssh en cours. Fermeture automatique quand tous ont réussi, sinon la fenêtre reste ouverte sur les échecs. Aucune sonde périodique : tout part d'un clic.
- **Options avancées à distance** : `RemoteSettingsDialog` lit l'état en **une seule connexion SSH** (`rpm-ostree kargs`, repli `cat /proc/cmdline`, plus la présence de `/etc/modules-load.d/gablue-cpuid-emu.conf`) et propose les mêmes quatre cases qu'en local, appliquées par les mêmes helpers (`sudo -n gablue-kargs`, `gablue-cpuid-emu`). **sudo à distance** : `remote_helpers_nopasswd()` sonde `sudo -n gablue-cpuid-emu status` (0 = règle NOPASSWD présente) ; sinon `QInputDialog` (écho masqué, jamais enregistré) puis `sudo -S -p '' -v` valide le cache une fois — le mot de passe part sur **stdin du ssh**, jamais dans argv — et le reste du script utilise `sudo -n`. Le chemin sert aussi au redémarrage et à l'extinction. `sudo -n true` ne sert PAS de sonde : aucune règle pour `true`, même sur Gablue ; `sudo -l` rend 0 dans tous les cas.
- **Redémarrage requis** (troisième pastille du pied de page, entre « Serveur SSH » et l'annonce locale) : visible seulement quand `local.pending_reboot_reasons()` rapporte quelque chose — image ostree `staged` (`rpm-ostree status --json`), kargs du prochain démarrage différents de `/proc/cmdline` (`BOOT_IMAGE=` écarté : il n'existe que côté noyau en cours, sinon tout poste semblerait en attente), configs écrites **après le démarrage** (`/etc/modprobe.d/wl-enable.conf`, `/etc/profile.d/vulkan-low-latency.sh` — une nouvelle session suffit pour celui-ci —, `/etc/modules-load.d/gablue-cpuid-emu.conf` et son blacklist — le test se nettoie tout seul au reboot suivant, aucune date figée, et une config livrée par l'image ne compte pas), et module `cpuid_fault_emulation` encore chargé alors que sa persistance a été retirée. Relu à chaque passe de 30 s dans `RebootWorker` (hors thread GUI, `rpm-ostree status` ~70 ms) : l'indication **survit à la fermeture de l'app**, rien n'est mémorisé côté session. Clic → confirmation listant les raisons → `privileged_prefix()` + `systemctl reboot` lancé détaché. Pas d'équivalent par poste distant : cela demanderait une connexion SSH par poste à chaque passe (la sonde de 30 s ne renvoie que l'état) ; piste = greffer la lecture sur la connexion existante ou la mettre en cache plusieurs minutes.
- **Recherche sur le réseau local** : `avahi-browse -rtp _ssh._tcp` dans une liste à cocher **vide au départ** — rien n'entre dans le registre sans validation explicite (bouton « Ajouter (N) » désactivé tant que rien n'est coché, « Tout cocher » pour l'inverse) ; la recherche propose, elle n'ajoute pas. C'est une entrée du menu du bouton **« Ajouter un poste »** (avec la saisie manuelle), pas une commande séparée. **Une ligne par machine, pas par adresse** : Avahi annonce une adresse par interface du poste (boucle locale, `docker0`, `tailscale0`, LAN…), d'où quatre lignes pour un seul poste constaté le 05/11/2026. `hosts.group_candidates` écarte ce qui n'est pas joignable d'ici — boucle locale, `169.254/16`, **nos propres adresses** (une adresse identique à la nôtre est forcément l'interface du poste, pas la sienne), et toute adresse hors de nos sous-réseaux directs **sauf Tailscale** (`100.64.0.0/10`) — puis regroupe par nom mDNS + utilisateur + port et trie LAN avant Tailscale (l'adresse LAN est le défaut). L'interface locale est lue par `ip -o -4 addr show` (`hosts.parse_local_ipv4`, table vide = filtre permissif). Dans le dialogue, un poste à plusieurs adresses affiche une liste déroulante (« 192.168.1.109 (LAN) », « 100.64.0.45 (Tailscale) ») : c'est l'adresse choisie qui est enregistrée. Un poste déjà connu par **n'importe laquelle** de ses adresses (`hosts.known_targets` / `candidate_known`, toutes les adresses du registre, pas seulement la principale) **reste affiché** dans la liste avec le suffixe « déjà ajouté », grisé et non cochable : une seconde découverte qui retombait sur un poste connu affichait une liste vide, ce qui se lisait comme une panne (vécu 07/11/2026). Il n'est ni compté dans la sélection ni coché par « Tout cocher ». Les adresses non choisies ne sont plus jetées : elles deviennent les `addresses` de secours du registre. Un poste coché n'est ajouté **qu'après vérification de sa clé** (voir « Copie de clé ») : la découverte ne suffit pas, un poste dont la clé ne passe pas n'entre jamais dans la liste.
- **Adresses du poste** (`hosts.remote_addresses`) : après une connexion réussie (installation de clé, ou premier état en ligne), le manager demande au poste son adresse LAN (`ip -4 route get 1.1.1.1`, donc pas `docker0`) et son adresse Tailscale (`tailscale ip -4`), puis les fusionne dans `addresses` (une fois par session et par poste, **tant qu'aucune adresse Tailscale n'est connue** — `util.has_address_kind`, sinon un poste ajouté en mDNS avec un secours LAN ne recevait jamais son adresse Tailscale). Le poste fait foi pour les types qu'il rapporte : une adresse Tailscale ou LAN périmée est **remplacée** au lieu de s'empiler (nœud réauthentifié, bail DHCP changé), seule l'adresse principale du registre n'est jamais retirée. C'est la seule façon de connaître l'adresse Tailscale d'un poste : Avahi n'annonce pas `tailscale0` de façon fiable — gen1 n'apparaissait qu'en LAN le 06/11/2026.
- **Serveur SSH local** : pastille au pied de page, `systemctl is-active`/`is-enabled`, bascule `sudo -n systemctl enable|disable sshd.service --now` (même effet que `ujust ssh-on/off`), **blanchi aux arguments exacts** dans `/etc/sudoers.d/nopasswd` (unité figée, pas de joker) donc sans mot de passe sur Gablue ; hors image, repli `pkexec` via `QProcess` (dialogue PolicyKit, bouton désactivé pendant l'attente) — jamais de `sudo` bloquant sur le thread GUI.
- **Annonce locale de ce poste** : seconde pastille du pied de page, lit la présence de `/etc/avahi/services/ssh.service` et l'état d'`avahi-daemon`. Activation et désactivation passent par `/usr/libexec/gablue-avahi on|off` (NOPASSWD, `status` pour la lecture) : il écrit lui-même le XML `_ssh._tcp` port 22 (`<name replace-wildcards="yes">%h</name>`, 0644, temporaire + `mv`) ou le retire. Un `sudo install` sur un fichier temporaire **ne pouvait pas** être blanchi aux arguments exacts (chemin aléatoire) et faisait donc ouvrir le dialogue PolicyKit à chaque bascule — vécu 06/11/2026. Avahi surveille le dossier et recharge seul (~1 s), aucun `systemctl restart`. Même schéma `sudo -n` → `pkexec`. **Pourquoi ce bouton** : le preset Fedora active bien `avahi-daemon`, mais `/usr/share/avahi/services/` est vide — sshd n'est donc jamais annoncé et la découverte de `gablue-manager` ne trouve rien sur un poste stock. L'annonce est **lien-local** (multicast `224.0.0.251:5353`, non routé) et ne publie que nom d'hôte, IP et port — aucun compte, aucune clé ; un poste qui s'y ferait passer pour un autre est bloqué par l'épinglage d'empreinte. Daemon arrêté → la pastille le dit et refuse la bascule (`sudo systemctl enable --now avahi-daemon`).
- **Bureau distant — relance sans erreur** : chaque clic ouvre une **nouvelle fenêtre**, même si une session tourne déjà (une seule session KRdp par utilisateur : le nouveau client coupe le précédent et sort en **2**, `STATE_RUN_QUIT`). Le code 2 est ignoré, comme le 131 de fermeture normale de `sdl-freerdp`, sinon un faux dialogue « La commande a échoué (code 2) » apparaissait à chaque reconnexion. Les sessions lancées par l'app restent suivies par poste (`host_id`, `kind="remote"`) : l'entrée **« Fermer la session de bureau distant »** du menu **Configuration** n'est active que s'il y en a une, demande confirmation (défaut : non), puis envoie SIGTERM au groupe (SIGKILL après 3 s) pour que `gremote` nettoie tunnel SSH, serveur RDP et puits audio ; fermer la fenêtre à la main la désactive au poll suivant. Supprimer un poste ferme ses sessions.
- **Page d'un poste (locale ou distante)** : quatre panneaux — la carte d'identité (locale : nom d'hôte, `utilisateur@hôte · distro`, « Ce poste », et le bouton **Configuration** ; distante : nom, adresse, état, Bureau distant / Fichiers / Terminal, bouton **Configuration** ; sur sa page, une **croix ✕ de 30 px**, seule au-dessus de la carte (`QToolButton#pageClose`), ramène à la liste), **« Mises à jour »** (détail par domaine, versions gwine avant → après, image staged ; boutons **« Vérifier »** et **« Mettre à jour »** côte à côte, le second portant le menu des domaines ; statut court « 2 disponibles » ou « À jour · image déployée aujourd'hui », et « À jour, sauf N domaine(s) non vérifié(s) » dès qu'une sonde n'a pas conclu (un échec ne se lit jamais comme « à jour », vécu 08/11/2026), les lignes « à jour » ne sont pas répétées, et la carte ne redit plus « aucune mise à jour disponible — Gablue mis à jour aujourd'hui »), **« Matériel et système »** (`InfoPanel` — son titre porte un **bouton ↻** : localement il relit tout (`_load_hardware`, hors thread, bande d'activité, bouton grisé pendant la lecture), sur un poste distant c'est une connexion SSH, `_load_remote_hardware(force=True)`, et un poste qui refuse la clé ou dont l'empreinte est inconnue n'en reçoit pas une de plus. Modèle ou **carte mère** quand le produit DMI est générique, BIOS, processeur, GPU au **nom commercial** lu par Vulkan (repli `lspci`) suivi de sa **VRAM** (`mem_info_vram_total` d'amdgpu ou `/proc/driver/nvidia`, arrondie à la taille commerciale ; « VRAM » seulement si `mem_info_vram_vendor` prouve de la mémoire dédiée, sinon « Gio (RAM allouée) » — sur un APU la valeur est une tranche de RAM réservée par le BIOS, pas de la mémoire en plus), **mémoire utilisée sur le total avec le pourcentage** (`MemTotal` − `MemAvailable`, le cache n'est pas compté), barrettes — nombre, taille, marque, type, fréquence — via le helper NOPASSWD `gablue-hwinfo` (absent → ligne vide), disques, **températures et verdict SMART** — un bloc **à droite sous la grille**, les disques à gauche (deux blocs côte à côte : empilés, ils laissaient un trou sous « Secure Boot » ou repoussaient « Disques »), masqué quand aucun capteur n'existe (un iGPU Intel n'en a pas) ; son étiquette devient « Températures et SMART » dès qu'un ✓/✗ est affiché, « Températures » sinon : CPU/GPU/NVMe lus dans `/sys/class/hwmon` sans privilège (`k10temp`/`coretemp` → `Tctl`/`Package id 0`, `amdgpu`/`nvidia` → `edge`/`temp1`, `nvme`/`drivetemp` → `Composite`, affiché « SSD » puis « SSD 1 », « SSD 2 » dès qu'il y en a plusieurs — un périphérique hwmon par SSD ; `spd5118`/`jc42` → `RAM 1`, `RAM 2` pour les barrettes) et disques SATA **plus leur verdict SMART** (`✓` quand `smartctl -H` passe, `✗` sinon, rien quand le disque ne le publie pas) par le helper `gablue-hwinfo` (`smartctl -n standby,3 -d sat -j -H -A`) : lus **au démarrage et sur le bouton ↻** du panneau (`refresh_requested`), en même temps que les barrettes — jamais dans la passe de 30 s, `/sys` est gratuit et `smartctl` non ; un disque **en veille n'est jamais réveillé**, il n'apparaît simplement pas, et son nom vient du point de montage (« hdd1 », « data2 ») ou du périphérique (« sdc ») s'il n'est pas monté. La case affiche **une ligne par famille** (CPU, GPU, SSD, HDD, RAM) et trois mesures par ligne au plus : six disques SATA ne tenaient pas sur une seule (constaté sur sucina), et une ligne par disque prendrait toute la hauteur — les espaces internes à une mesure sont insécables, donc « HDD 5 (hdd5) 38 °C » n'est jamais coupé. Les disques sont triés par **ordre naturel** (`hdd1, hdd2, hdd10`) : le helper les rendait « 3 2 1 », à l'envers (vécu 08/11/2026). Chaque disque porte le nom de son montage entre parenthèses (`disk_labels`, tiré de la page « Disques ») : « SSD 1 (Système) », « SSD 2 (ssdtemp) », « HDD 1 (hdd1) » — « SSD 2 » seul ne disait pas de quel disque il s'agissait, et les montages ne portent pas les mêmes noms d'un poste à l'autre (« data2 », « films »). Les SATA sont donc numérotés comme les SSD (`HDD 1`, `HDD 2`) et le disque qui porte `/` ou le dossier personnel s'appelle « Système ». Les lignes sont **empilées** (pas de colonnes : côte à côte, le SSD se lisait sur la même ligne que le CPU) et composées **comme une ligne de disque** : le nom (« CPU », « SSD 1 (Système) », « HDD 2 (hdd2) ») au corps des valeurs (13 px, clair) puis la mesure (« 48 °C », « 37 °C ✓ ») en gris (11 px), les mesures d'une même ligne espacées de 12 px — un texte uniforme à 11 px paraissait écrit plus petit que le bloc d'en face, et à 13 px plus gros (vécu 08/11/2026). Découpage par `local.temperature_measures` : le séparateur de mesures est une double espace, et le nom peut lui-même contenir une insécable (« SSD 1 »), donc on coupe devant le chiffre, jamais au premier séparateur. Hauteur de ligne 15 px et interligne 16 px, identiques aux disques, et un ressort final garde les lignes serrées même quand le bloc voisin étire la cellule. La grille s'arrête à **10 champs, 5 rangées pleines** (modèle ou carte mère, BIOS, processeur, GPU, mémoire, barrettes, noyau, image Gablue (« actuelle X · déployée aujourd'hui », ou « actuelle X · en attente Y » quand une image attend le redémarrage — jamais « nouvelle image en attente » sans version), système, démarrage) : **Secure Boot ouvre la colonne de gauche, au-dessus de « Disques »**, sinon la 11e rangée laissait la colonne de droite vide et « Disques » descendait sous un trou de 65 px (vécu 08/11/2026)), et l'**accès local** (SSH + annonce mDNS) au pied de l'onglet « Postes SSH ». **Disques** : une ligne par périphérique (un seul point de montage par source, celui du home en priorité), espace libre/total, pourcentage **utilisé** écrit en clair (« 87 % utilisé », rouge dès 90 %) — la ligne parle de Gio libres, un « 87 % » nu se lisait à l'envers. Les chiffres libres/total forment un **lien cliquable** (`ClickLabel`) qui ouvre Filelight sur le montage — sur le **home** pour le disque du système (`mount == "/"` ou porteur du home), jamais sur `/usr` ; le bouton « Libérer de l'espace » est retiré (une ligne de boutons par disque doublait la hauteur de la section), les lignes sont donc serrées comme celles des températures. **Synthèse** collée à la dernière ligne de disque dès qu'il y a plusieurs disques, sur la **même forme** qu'une ligne de disque : « Total : 2 Tio libres sur 13 Tio   85 % utilisé » (somme des disques affichés — les points de montage d'un même périphérique sont déjà fusionnés, aucun double compte). Filelight ne lit que la machine courante : pas de lien sur un poste distant. Le résumé matériel distant vient de `remote_hardware.py` (une connexion SSH, sections `::gablue:*`, analyse locale réutilisée) via `RemoteHardwareWorker`, chargé au premier affichage de l'onglet et **pas** sondé en fond ; un poste qui refuse la clé ou dont l'empreinte est inconnue n'est pas sondé (`NO_AUTO_PROBE_STATES`).
- **Configuration du poste local** : la carte du poste local (supprimée puis **remise** le 07/11/2026 — un bouton seul en haut de l'onglet faisait orphelin) reprend les métriques d'une carte de poste (hauteur 92, icône dans un emplacement de 26 px, mêmes marges) et ne porte qu'un bouton **« Configuration »** libellé, comme une carte distante. Il suit exactement l'ordre d'un menu de poste distant : **Réglages ▸** (Noyau et matériel, Services et pilotes, Mises à jour automatiques, Variante de l'image, **Démarrage ▸** — Menu GRUB, Secure Boot —, **Jeux ▸** — Options de gwine, Priorité au premier plan —, **Réseau ▸** — Tailscale, puis serveur SSH et annonce locale dont le libellé dit le geste —, puis **Compression Btrfs…**, **Limite thermique NVMe…** et la limite de température CPU quand le poste est un Ryzen), **Nettoyer le système…** (action directe : un sous-menu « Maintenance » à une seule entrée n'apprenait rien), **Applications…**, puis après un séparateur **Actions ▸** (Démarrer sur un autre système, Redémarrer dans le BIOS). Tout ce qui se règle est dans « Réglages », y compris le démarrage et les limites thermiques : ce ne sont pas des catégories concurrentes, et un poste distant range déjà Jeux et Réseau là. Chaque dialogue applique ses changements d'un coup ; le booster au premier plan est un réglage de jeu, il vit avec les options de gwine. Le bouton **Configuration** d'un poste distant, libellé comme celui de la carte locale (le ⋯ muet ne disait pas ce qu'il ouvrait, vécu 07/11/2026), reprend la même carte mentale : **Réglages ▸** (Noyau et matériel, Jeux ▸ Options de gwine + Priorité au premier plan, Réseau ▸ Tailscale, puis Compression Btrfs et Limite thermique NVMe), **Nettoyer le système…** en action directe, **Applications…**, puis **Actions ▸** (Fermer la session de bureau distant, Redémarrer, Éteindre, Installer la clé SSH, Modifier, Supprimer) — le cycle de vie du poste ne se mêle pas à sa configuration. Bios, GRUB, Secure Boot et le choix d'un autre système restent strictement locaux : ils touchent le firmware ou l'amorçage, pas la session. Chaque outil distant lit son état en **une seule connexion SSH** (sonde `REMOTE_*_PROBE`) et applique par `RemoteTaskDialog` (`progress_mode="busy"`, journal derrière « Terminal ») ; le mot de passe sudo n'est demandé que si le poste n'a pas la règle NOPASSWD (`remote_helpers_nopasswd`, puis `remote_sudo_prefix`). `RemoteTaskDialog` n'accepte pas `progress_parser` : les scripts distants n'émettent aucun marqueur `::gablue:`. Menu **« Mettre à jour »** : image Gablue (`bootc upgrade`, appliquée au prochain démarrage), Flatpaks (`sudo -n flatpak update --system -y` — Gablue n'installe qu'au niveau système, aucun `--user` ; la règle sudoers de l'image évite tout mot de passe, hors image Gablue repli sur l'appel direct et son dialogue PolicyKit), gwine (`gwine --init` : runner et composants DXVK/VKD3D, init seulement si un composant a changé) et Homebrew (`brew update` puis `brew upgrade`, même préfixe que les timers, `HOMEBREW_NO_AUTO_UPDATE=1` pour ne pas doubler l'update, aucun privilège), et **applications** (`Applications (AppImages)…` : sonde réseau hors fil graphique via `apps.pending_updates`, puis les scripts d'installation des seules applications en retard, une par une, avec un marqueur `::gablue:step` **et** `::gablue:busy` par application — `step` pose le plancher `(i-1)/N`, `busy` fait balayer la barre pendant le téléchargement, qui n'a aucun pourcentage exploitable (cURL change de forme selon le script : `--progress-bar` pour ES-DE, jauge classique ailleurs), et le libellé nomme l'application en cours (`(i/N)`), sinon une application unique laissait un « 0 % » figé pendant tout le transfert, vécu 08/11/2026 ; `apps.update_script` ouvre par `set -e`, donc une application en échec arrête la suite et le code de sortie est celui de la **première** qui a échoué, plus celui de la dernière qui a réussi ; rien à mettre à jour ou flux muet → message, aucune réinstallation inutile). Le journal de `bootc upgrade` est traduit par `local.gablue_update_hint` (local et distant, seul le compte rendu d'upgrade compte, pas `bootc status`) : « déjà à jour » quand bootc répond « No changes in… », « rien de nouveau à télécharger, une image est déjà en attente » quand il ajoute « Staged update present, not changed » — chercher « staged » sans ce cas annonçait une nouvelle image après un no-op (vécu 07/11/2026) — et « redémarrage nécessaire » seulement sur « Queued for next boot »/« Upgraded ». La mise à jour **locale** affiche en plus une **barre de progression** alimentée par le JSONL de bootc (`--progress-fd`) et un bouton **« Terminal »** qui révèle le journal (masqué par défaut) : `/usr/libexec/gablue-update` (NOPASSWD, sans argument) crée `/run/gablue/update-progress.fifo` et y branche bootc, parce que sudo ferme les fd ≥ 3 ; l'app lit le FIFO sans privilège (`QSocketNotifier`, tâche `ProgressBytes`/`ProgressSteps` traduite par `local.parse_progress_event`, octets quand le total est connu, sinon étapes, sinon barre indéterminée ; **seuls `bytes` et `steps` comptent** — `bytesCached`/`stepsCached` sont le déjà-présent cumulé d'exécutions précédentes, les additionner donnait « 4,0 Gio / 772 Mio » et une barre à 100 % dès le premier événement (vécu 08/11/2026, bootc 1.17.1) ; le helper retire son FIFO à la sortie (`trap EXIT`) et tue bootc lui-même sur `TERM`/`INT`/`HUP` (TERM puis KILL) — sans quoi « Annuler » ne coupait que sudo et le helper quand sudo isole la commande dans son pty, et bootc téléchargeait encore (vécu 08/11/2026) et l'app ignore un FIFO plus ancien que son lancement (instant **remis à chaque étape** dans « Tout mettre à jour… », sinon le garde-fou y était inerte : `_progress_started` restait à 0), sinon une mise à jour annulée laissait un tube mort relu comme celui de l'opération suivante). Repli sur `bootc upgrade` direct quand le helper manque (image antérieure) : bootc est alors muet, la fenêtre garde la même présentation avec une barre **indéterminée** (et dans « Tout mettre à jour… », une étape `busy` fait balayer la barre globale au lieu de la figer). La mise à jour **locale des Flatpaks** a le même traitement, sans helper : hors terminal flatpak écrit « Updating 3/7… » puis réémet la ligne avec un pourcentage (`local.parse_flatpak_progress`, msgid anglais non traduits en fr — vérifié 07/11/2026, flatpak 1.18.4), `LocalTaskDialog(progress_parser=local.parse_flatpak_progress)` en tire une barre globale à la phase — `(op-1 + pct/100)/total` — et masque le journal derrière le même bouton **« Terminal »** ; Une seule phase (système), la barre ne redescend plus. `local.flatpak_update_hint` ne conclut « Aucune mise à jour disponible. » que si aucune opération n'a démarré (la phase système dit presque toujours « Nothing to do. »). **Homebrew n'a pas d'équivalent en pourcentage** : hors terminal `curl` est lancé en `--silent` (`utils/curl.rb`, Homebrew 7.0.12 vérifié 07/11/2026), donc aucune jauge ni débit, et la file de téléchargements concurrente ne rend que des lignes de fin. `local.brew_progress_parser()` (analyseur stateful, un par fenêtre) donne donc une barre **par formule** : `Fetching downloads for: a, b` fournit la liste (donc le total, Homebrew 7 ne résumant qu'après) avec une barre indéterminée faute de pourcentage, puis chaque `Upgrading <nom>` avance d'un cran — les lignes `… dependency: <dep>` ne comptent pas ; `local.brew_update_hint` dit « Aucune formule à mettre à jour. » quand `brew upgrade` n'écrit rien. **« Tout mettre à jour… »** (en tête du menu) enchaîne les étapes **disponibles** dans une seule fenêtre `tasks.SequentialTaskDialog` : image Gablue (helper/FIFO ou `bootc upgrade`), Flatpaks, gwine, **applications** puis Homebrew, chacune gardant son analyseur ; les applications n'ont pas d'état local, donc leur sonde réseau (`apps.pending_updates`, hors fil graphique, bande d'activité pendant ce temps) part **avant** d'ouvrir la fenêtre et la confirmation liste la séquence exacte (noms des AppImages compris) — étape omise quand tout est à jour ; Homebrew reste en dernier parce que c'est l'étape la plus longue et la plus fragile, un échec ne doit pas laisser les AppImages en retard ; la barre **globale** vaut `(étapes terminées + fraction courante) / total`, un outil absent est omis (pas une erreur), et un échec arrête la suite en laissant la fenêtre et le journal ouverts (barre plancher aux étapes accomplies). Quand aucun pourcentage n'est disponible (téléchargements de brew, bootc sans total, attente avant le premier événement), la barre bascule sur **`widgets.BusyProgressBar`** : un segment peint qui balaie la piste de gauche à droite, parce qu'un `QProgressBar` en mode indéterminé (`range(0,0)`) ne s'anime pas sous feuille de style Qt ; le mode déterminé est habillé par le QSS (`#taskProgress` : même piste arrondie, chunk accent, pourcentage centré ; les **barres de défilement** aussi — `QScrollBar` poignée arrondie sur piste transparente, sans flèches, accent au clic : sans ces règles Qt peint la sienne, noire, qui jure avec le reste, constaté 08/11/2026 dans le journal des tâches), le timer s'arrête barre masquée, et la bande d'activité de 3 px de l'en-tête utilise le même widget — toujours montée (`set_active`, jamais `setVisible`) pour que l'interface ne descende plus de 3 px à chaque vérification, et **seul un rafraîchissement demandé** (F5) l'allume : une passe automatique (timer, retour sur la fenêtre, ouverture d'une page) reste invisible. Chaque action est confirmée puis suivie dans `LocalTaskDialog` (QProcess, canaux fusionnés, annulation par `setsid` (le groupe entier est tué : `sudo`, `bash` et `bootc` ensemble, sinon « Annuler » laissait bootc télécharger — vécu 08/11/2026 ; jamais le groupe de l'app elle-même), codes 125/126/127 traduits). Le bouton **« Mettre à jour » du panneau « Mises à jour »** devient « Mettre à jour (N) » ; sur la carte de la liste « Postes SSH », les entrées de son menu portent leur compte ; **« Vérifier les mises à jour »** en tête du menu lance une sonde immédiate (domaines cochés dans les préférences, même si la surveillance automatique est coupée) ; le bouton **« Vérifier les mises à jour »** de l'en-tête n'existe plus : l'onglet « Postes SSH » porte **un seul bouton « Mises à jour des postes »**, menu à deux entrées (« Vérifier les mises à jour », « Tout mettre à jour… ») ; **plus de bouton « Rafraîchir l'état »** (la passe automatique de 30 s et le retour sur la fenêtre suffisent), **F5** force la sonde de l'onglet courant ; côté local, c'est le bouton « Vérifier » du panneau « Mises à jour » qui sonde ; **aucun texte « Vérification… » pendant une passe de rafraîchissement** : la pastille pulse et la ligne garde « En ligne · N ms » jusqu'à la réponse, seule la latence change (un texte de largeur différente faisait sauter la carte).
- **Applications** (entrée « Applications… » du menu **Configuration** — bouton « Configuration » de la carte locale, bouton « Configuration » d'une carte de poste — **plus de bouton dédié nulle part** : la carte locale ne garde que Configuration, la distante garde Bureau distant / Fichiers / Terminal et son bouton Configuration) : dialogue **non modal** en deux sections, « Émulateurs » (ES-DE, Azahar, Eden, Xenia, Lichii) et « Outils » (OpenCode 2), avec pour chaque ligne l'état (AppImage `~/AppImages`, version GearLever, version CLI quand il y en a une), un bouton **Installer/Mettre à jour** et **Supprimer**. **Local et distant** partagent le même dialogue (`host=None` ou un poste) : à distance l'état est lu en **une seule connexion SSH** (`REMOTE_STATE_SCRIPT` : GearLever, `ls ~/AppImages`, `opencode --version`, chemins des scripts + options qu'ils connaissent, découpé par `parse_remote_state`/`remote_states`) et les actions passent par `RemoteTaskDialog`, jamais par un `exec()` ; poste injoignable → lignes « État indisponible » et boutons désactivés. Aucune logique de téléchargement n'est réimplémentée : le manager lance le script existant de l'image (`esde-install`, `azahar-install`, `eden-install`, `xenia-install`, `lichii-install`, `opencode2-install`) et affiche son journal derrière le bouton **« Terminal »** (barre indéterminée, journal révélé à l'échec, en local comme à distance ; **une annulation ne montre jamais le journal et referme la fenêtre** — arrêter est le résultat, pas la peine d'afficher un journal tronqué) ; ES-DE reçoit `--yes` (le journal remplace ses boîtes kdialog) et expose en plus **« Mettre à jour la config »** (`--config-only` : `custom_systems` + lanceurs Tools, sans toucher à l'application). **Le manager lit le script pour savoir ce qu'il accepte** (`script_has_option`, jamais en l'exécutant ; à distance, `grep` dans la sonde) : un `esde-install` plus ancien que le paquet ignore les arguments inconnus et lancerait l'installation interactive (« ES-DE semble déjà installé… », constaté) — en local le manager fait alors la copie lui-même (`copy_esde_config`, même règle : `~/ES-DE/custom_systems`, `<ROMDirectory>/tools/`, lanceur existant non écrasé), à distance il refuse avec un message « mettre à jour l'image du poste » (la copie ne peut pas être faite à moitié à travers SSH). La suppression est générique (retrait GearLever, AppImage, `.desktop`, icônes) sauf OpenCode 2, qui passe par `opencode2-remove` (CLI npm, symlink, entrées Dolphin + `mimeapps.list`, MCP Lightpanda) : **configuration, sauvegardes, jeux et sessions ne sont jamais touchés** (`~/ES-DE`, `~/Roms`, `~/.config/opencode`, `~/.config/ai.opencode.desktop`, `~/.local/share/opencode`). Supprimer OpenCode 2 arrête son serveur de fond — donc les sessions ouvertes sur ce poste (y compris une session lancée par SSH) ; `opencode2-remove` absent du poste → suppression désactivée (pas de retrait à moitié). GearLever absent → installation/mise à jour désactivées, suppression toujours possible ; script absent de l'image → bouton désactivé avec l'explication en infobulle. Les six cartes défilent (`QScrollArea`) pour tenir sur un écran 800 px. **Mises à jour détectées en fond** : à l'ouverture et après chaque installation/suppression, un `_LatestWorker` (QThread) interroge la dernière version publiée des seules applications **installées**, puis `_apply_rows` ajuste le bouton — pendant la sonde, `_checking` impose « Vérification… » **grisé** (aucun verdict prématuré), puis « Mettre à jour » actif avec la version en infobulle, ou « À jour » **vert et désactivé** (`QPushButton#ok`) quand la version installée est la dernière. Aucune requête à `api.github.com` (quota anonyme 60 req/h par IP, partagé par tout le réseau) : flux **Atom** des releases GitHub/GitLab, API Gitea pour Eden, registre npm pour OpenCode. Comparaison de version pointée quand les deux côtés en ont une (le titre du flux fait foi : « AzaharPlus 2126.2-A » → 2126.2), sinon date de publication de la release contre date du fichier installé (`mtime`, lu par `stat` en local et à distance) — les tags qui sont des hachages (Xenia) passent par la date, et les flux qui mélangent plusieurs applications sont filtrés par titre (`latest_filter` de Lichii, dont le flux porte aussi les releases Eglantine ; ses titres « Lichii nx2 build 117 » n'ayant pas de version pointée, c'est le tag `build-117` qui sert de version). Dans le doute (flux muet, réseau), le bouton reste « Mettre à jour » actif : on ne dit jamais « à jour » à tort.
- **Noyau et matériel** (`Noyau et matériel…`, ex-« Réglages du noyau », local et distant) : dialogue d'`dialogs/kernel.py` à **cinq cases à cocher** — protections contre les failles du processeur (`mitigations=off`), correctif CPUID pour certains jeux (`clearcpuid=514`, ex-`ujust cpuid-fix-on/off`), mode ERTM du Bluetooth (`bluetooth.disable_ertm=1`), **HDMI 2.1 sur GPU AMD** (`amdgpu.dcfeaturemask=0x402`, ex-`ujust configure-amd-hdmi21`) et émulation CPUID fault (`cpuid_fault_emulation`, ex-`ujust cpuid-emu-on/off`) — avec un seul bouton **« Appliquer »**, actif seulement si une case diffère de l'état du poste. Les **quatre** kargs partent en **un unique** appel à `/usr/libexec/gablue-kargs` (un déploiement), l'émulation CPUID dans `/usr/libexec/gablue-cpuid-emu on|off` — réservée aux **PC AM4 et à la Steam Deck** (Ryzen 7000+ et Intel 4e génération et plus gèrent le CPUID faulting nativement) : le module `cpuid_fault_emulation` réalise cette émulation au niveau SVM et ne peut pas coexister avec `kvm_amd` ; fermer avec des cases modifiées demande confirmation. Les deux helpers sont en NOPASSWD : **aucune invite de mot de passe** sur un poste Gablue. Les cartes conseillées (protections, correctif CPUID, ERTM) portent une **pastille de conseil** (`recommendation_badge`/`set_recommendation`, `uiutil`) : **l'état conseillé** en vert quand le choix courant le suit (« ✓ Conseillé : activé|désactivé », repris de `CHOICE_STATE`), **le geste** en orange quand il s'en écarte (« Conseillé : à activer|à désactiver », « choisir X11 ») — **le texte dit l'écart**, la couleur ne fait que le renforcer (une couleur seule se lisait mal). Un « ✓ Conseillé » nu, posé à côté d'une case décochée, se lisait comme « il est conseillé de cocher » : le vert nomme donc toujours la valeur. Elle disparaît tant que l'état est illisible. Conseil par case : protections activées, **correctif CPUID activé** (débloque des jeux sans coût ailleurs), ERTM désactivé. **HDMI 2.1 et l'émulation CPUID fault n'ont pas de conseil** : ce sont des opt-ins explicites — selon l'écran (FreeSync et fonctions 2.1, mais scintillements possibles) ou selon le jeu sur un PC AM4 / une Steam Deck. **L'état lu est celui du prochain démarrage** (`rpm-ostree kargs`, sans root), pas `/proc/cmdline` qui décrit le noyau en cours — sinon les cases reviendraient à l'ancienne valeur juste après l'application ; l'émulation est lue dans `/etc/modules-load.d/gablue-cpuid-emu.conf`. Les kargs ne prennent effet qu'au redémarrage, le dialogue le dit.
- **Services et pilotes** (`Services et pilotes…` du menu **Configuration** de la carte locale) : dialogue local d'`dialogs/services.py`, ex-recettes ujust. **Six cases** — DisplayLink (service), Docker, couche Vulkan low-latency, pilote Wi-Fi Broadcom `wl`, historique atuin, **raccourcis manette Gablue** — avec un seul **« Appliquer »** et la valeur recommandée affichée (low-latency activé). **DisplayLink, Docker, le Wi-Fi Broadcom et atuin n'ont pas de recommandation** : les trois premiers dépendent du matériel du poste ou d'un service désactivé par défaut — une pastille y dirait « décochez » à qui a justement le dock ou la carte — et atuin relève d'un choix d'historique, pas d'un réglage de confort. **Docker n'est affiché que sur une variante DX** (`docker_available(variant)`, suffixe `-dx`) : ailleurs le paquet n'existe pas. L'état des cases vient de `systemctl is-enabled`, de la présence de `/etc/profile.d/vulkan-low-latency.sh` et de `/etc/modprobe.d/wl-enable.conf`, et de `atuin init bash` dans `~/.bashrc` ; l'application passe par `/usr/libexec/gablue-service`, `gablue-low-latency` et `gablue-broadcom-wl` (sudo -n) puis `/usr/bin/gablue-atuin` (sans privilège, fichiers de l'utilisateur) — un seul script, une seule tâche. **Atuin** : `on` installe ble.sh et branche un bloc balisé dans `~/.bashrc` (les lignes héritées d'ujust sont fondues dedans, jamais dupliquées) — l'`eval` porte **`--disable-up-arrow`** pour que la flèche Haut reste à ble.sh (historique du shell) et qu'atuin ne s'ouvre que par Ctrl-R, configuration du poste de référence (05/11/2026) ; `off` retire le bloc et ble.sh, avec instantané `~/.bashrc.gablue-atuin.bak`, mais **ne touche jamais** `~/.local/share/atuin` (historique) ni `~/.config/atuin`. Si les helpers ne sont pas dans l'image, les cases sont désactivées avec « reconstruction requise » plutôt que de lancer des commandes absentes. La **variante d'image** a son propre dialogue (`dialogs/variant.py`) : un rebase est un geste lourd et destructeur, il ne cohabite plus avec des bascules réversibles. Les **raccourcis manette** (actifs par défaut via `/etc/xdg/autostart/gablue-gamepadshortcuts.desktop`) passent par le helper utilisateur `/usr/bin/gablue-gamepad on|off|status` : `off` pose `~/.config/autostart/gablue-gamepadshortcuts.desktop` (`Hidden=true`, mécanisme XDG du panneau Plasma) **et** arrête le lanceur + le binaire en cours (sinon ils survivraient jusqu'à la déconnexion) ; `on` retire le masque et relance tout de suite. Aucun privilège, effet immédiat ; helper absent de l'image → case grisée sans condamner les autres.
- **Mises à jour automatiques** (`Mises à jour automatiques…` du menu **Configuration**, `dialogs/updates.py`) : **opt-in** — l'image livre tous les timers **désactivés** (`files/scripts/systemd`), c'est l'utilisateur qui choisit. Trois cases indépendantes (image Gablue, Flatpaks système, Homebrew) et **une fréquence par domaine** (quotidien ou hebdomadaire, 04:00, sans réveiller la machine) — l'intitulé est « Fréquence », pas « Rythme ». Application en une tâche : `/usr/libexec/gablue-auto-update image|flatpak|brew on|off` et `schedule image|flatpak|brew daily|weekly` (sudo -n, formes exactes du sudoers) ; seules les fréquences modifiées sont écrites, puis `flatpak-user-update.timer` en `systemctl --user` (drop-in `~/.config/systemd/user/flatpak-user-update.timer.d/50-gablue-schedule.conf`, sans privilège, message si aucune session). L'état vient de `gablue-auto-update status` (`image=`, `flatpak=`, `brew=`, `image_frequency=`, `flatpak_frequency=`, `brew_frequency=`, parsé par `local.parse_auto_update_status`) ; tout passe par les timers système, Gablue ne met à jour que les Flatpaks `--system` (plus de timer du compte à basculer). Le calendrier est écrit dans `/etc/systemd/system/<timer>.d/50-gablue-schedule.conf` : `OnBootSec=`, `OnUnitInactiveSec=` et `OnCalendar=` sont **vidés** avant le nouveau calendrier, sinon `rpm-ostreed-automatic.timer` cumulerait ses propres déclencheurs avec le nôtre. Dialogue désactivé si le helper manque de l'image (`auto_update_available`).
- **Icône de barre d'état** (`gablue-manager --tray`, `tray.py` + `prefs.py` + `instance.py`) : lancée à l'ouverture de session par `etc/xdg/autostart/gablue-manager-tray.desktop`. Le mode ne charge **que** l'icône — pas de `MainWindow`, pas de registre des postes, aucune sonde SSH. **Clic = bascule** : la fenêtre tourne → elle se ferme (l'app se termine, plus rien ne sonde en fond) ; sinon elle est lancée. Le menu garde « Ouvrir Gablue Manager » (toujours `raise`). **Pastille rouge** (`badge_icon`, `#e01b24`, **34 %** du côté de l'icône) dès qu'un événement attend l'utilisateur : redémarrage requis (`RebootWorker`/`pending_reboot_reasons`, relu toutes les **5 min**) ou **mises à jour disponibles**. L'infobulle et le menu partagent `tray_lines()` : raisons de redémarrage en phrase (première lettre en capitale, doublon avec l'image staged retiré) puis une ligne par domaine, les deux en lignes courtes à puces dans l'infobulle. **Notification brève** (`QSystemTrayIcon.showMessage`, 8 s) : une passe automatique ne la signale que si le compteur de mises à jour **monte** — répéter « 3 mises à jour disponibles » toutes les deux heures serait du bruit, la pastille suffit ; une vérification demandée par le menu répond **toujours** (« N mises à jour disponibles » + les lignes concernées, « Aucune mise à jour » sinon, « Vérification des mises à jour — hors ligne » sans connexion), et le message `updates` venu de la fenêtre ne notifie pas (elle affiche déjà le résultat). Le menu est **reconstruit** à chaque changement (`aboutToShow`, jamais pendant qu'il est ouvert) : « Ouvrir Gablue Manager » en gras, sections `QMenu.addSection` « Redémarrage requis » et « Mises à jour » avec des lignes informatives désactivées, séparateur, puis « Vérifier les mises à jour » (grisé pendant la sonde) et « Quitter ». Instance unique par socket `gablue-manager-<uid>` / `gablue-manager-tray-<uid>` : `instance.claim` reprend une socket orpheline (processus tué), la fenêtre traite `raise` et `toggle`, le tray `quit`, `reload` (préférences changées), `updates` (mise à jour terminée dans la fenêtre → sonde forcée) et `state:<json>` : toute vérification terminée dans la fenêtre (`window._updates_done`) pousse son état, que le tray applique **tel quel** (`Tray.apply_state` — `updates.state_message`/`parse_state_message`) au lieu de refaire les mêmes sondes réseau : pastille, infobulle et menu disent le même chiffre que la carte dès cette vérification, sans attendre son timer (vécu 08/11/2026). Une sonde du tray déjà en vol garde la main (son résultat est plus frais), et un `state:` abîmé ou d'une autre version retombe sur les messages connus au lieu de casser. **Une seule fenêtre, jamais deux** : une relance passe par `instance.spawn(instance.manager_command())`, c'est-à-dire `python -m gablue_manager` de la **même version** avec son `PYTHONPATH` — jamais le `gablue-manager` du PATH, qui sur une image antérieure ignorait ses arguments et ouvrait une seconde fenêtre même pour `--tray` (vécu 07/11/2026). Pas de position fixe dans la barre : l'ordre appartient à Plasma.
- **Vérification des mises à jour** (`updates.py`, `workers.UpdateCheckWorker`) : cinq domaines indépendants, **dans l'ordre de la chaîne de mise à jour** — image Gablue, Flatpaks (système seulement), composants gwine (`gwine --init --check`), applications (AppImages gérées : `apps.pending_updates`, un flux de releases par application installée, jamais `api.github.com` ; aucune application installée → domaine « absent de ce poste », flux muet → « vérification impossible » plutôt que « à jour ») et Homebrew. `updates.DOMAINS` fixe cet ordre canonique (lignes du panneau, infobulle du tray, « N mises à jour : … ») et `prefs.CHECK_DOMAINS` le reprend pour les cases des préférences et les menus. L'image se lit sans réseau quand une mise à jour est déjà téléchargée (`staged` dans `rpm-ostree status --json`, qui donne aussi l'âge du déploiement amorcé = dernière mise à jour de Gablue) ; sinon `sudo -n bootc upgrade --check` (métadonnées seules, règle sudoers existante). La sortie de bootc nomme la version distante (`Version:`, vérifié avec 1.17.1) : le résumé l'affiche « actuelle X → Y », local et distant (`parse_bootc_version`) ; une sortie sans `Version:` retombe sur « actuelle X ». **Jamais de sonde hors ligne** : `uiutil.network_online()` interroge `QNetworkInformation` (NetworkManager par D-Bus) et la barre d'état saute la passe ; le retour de la connexion déclenche une sonde si le dernier état a plus de 5 min. Fréquence et domaines viennent des préférences (`check_interval` en minutes, défaut 120 ; `check_auto` + `check_image|flatpak|brew|gwine|apps`; le tray convertit cette fréquence en millisecondes pour `QTimer` — en secondes, l'intervalle de 120 min tombait à 7,2 s, vécu 08/11/2026) ; le menu du tray offre « Vérifier les mises à jour » (ignore l'interrupteur et la fréquence, pas la connexion). Résultats affichés dans le panneau « Mises à jour » de l'onglet local (`UpdatesPanel.set_updates` : statut court, une ligne par domaine hors « à jour », compteur sur « Mettre à jour (N) » ; l'âge du déploiement n'y est **pas** répété — il est dans « Matériel et système » et dans le statut, demandé le 08/11/2026), sur la carte d'un poste de la liste (`HostCard.set_updates` : infobulle et compteurs du menu) et dans le tray (pastille, infobulle, menu). **Une mise à jour lancée depuis l'app re-sonde aussitôt** (`_updates_after_task`, `force`) et prévient le tray par le message `updates` (sonde forcée de son côté) : sans cela le compteur et la pastille rouge gardaient l'état d'avant la mise à jour jusqu'au créneau suivant, 120 min par défaut (vécu 07/11/2026 : gwine à jour, toujours « 1 mise à jour » et point rouge). Toute autre vérification (`check_updates`, bouton « Vérifier », F5, retour sur la fenêtre) pousse de même son état au tray en fin de passe : la pastille ne dépend plus du seul timer, qui pouvait la laisser en retard de deux heures.
- **Préférences** (`Préférences…` du menu ⚙, `dialogs/prefs.py`) : `~/.config/gablue/preferences.json` (dossier 0700, fichier 0600, écriture atomique `mkstemp` + `os.replace`) — `tray` (icône de barre d'état), `check_auto` (surveillance), `check_image`, `check_flatpak`, `check_gwine`, `check_apps`, `check_brew` (ordre de `prefs.CHECK_DOMAINS`, celui des cases et des menus), `check_interval` (minutes, borné à 5…1440). Le mode tray relit le fichier à chaque sonde et sort au démarrage si `tray` est faux, sans toucher à l'autostart ; la fenêtre envoie `reload` au tray après application. « Appliquer » est **inerte tant que rien ne change** (bouton désactivé, garde dans `apply()`) : aucune écriture, aucun tray relancé.
- **Menu GRUB** (`Menu GRUB…` du menu **Configuration**, `dialogs/grub.py`) : équivalent graphique de `ujust configure-grub`. Trois choix exclusifs — toujours afficher (`menu_auto_hide` retiré), masquer après un démarrage réussi sauf en double-boot (`1`), masquer même en double-boot (`2`) — l'état courant (`grubenv`, souvent `0` ou absent) est affiché en clair et le bouton reste inactif tant que rien ne change (`0` et « non défini » ont le même effet). Écriture par `/usr/libexec/gablue-grub status|set 0|1|2|unset` en `sudo -n` (règles exactes, **aucune invite de mot de passe**) ; `grubenv` est en 0700 root, donc même la lecture passe par le helper. Le helper remet `/boot` en écriture si besoin puis restaure son état. Effet au démarrage suivant, le dialogue le dit.
- **Démarrer sur un autre système** (`Démarrer sur un autre système…` du menu **Configuration ▸ Démarrage**, `dialogs/boot.py`, **local seulement**) : liste les disques amorçables **autres que celui du système en cours** — entrées EFI déjà connues du firmware et ESP portant un chargeur mais jamais enregistrée (clé USB) — puis arme un démarrage **unique**. Le disque principal est identifié par `/boot/efi` (sinon `/`) et écarté des deux côtés (app et helper), jamais par le seul libellé ; un disque absent ou une entrée non-UEFI n'est pas proposé. `/usr/libexec/gablue-bootnext list|boot <id>` en `sudo -n` : `boot` revérifie l'identifiant côté root (4 hexadécimaux existants, ou `esp:/dev/sdX1` typé ESP et disque ≠ principal), crée au besoin une entrée NVRAM `Gablue : <nom> (<disque>)` puis la retire du BootOrder permanent (seul `BootNext` la porte), arme `BootNext` et redémarre. Le firmware consomme `BootNext` une fois : Gablue revient au démarrage suivant. Confirmation explicite ; le dialogue se ferme avant de lancer la tâche (modal) et le redémarrage interrompt la session.
- **Secure Boot** (`Secure Boot…` du menu **Configuration**, `dialogs/secureboot.py`) : état du firmware (`mokutil --sb-state`, sans privilège) et des deux certificats Gablue (`gablue-secure-boot.der` pour les kmods ublue-os, `gablue-kmod.der` pour les modules signés localement), lus par `/usr/libexec/gablue-secureboot status` en `sudo -n` (le dossier `/etc/pki/akmods/certs` est en 0700 root). « Programmer l'enrôlement » écrit la demande MOK (`… enroll`) ; elle prend effet **au démarrage suivant**, dans le menu MokManager, mot de passe public **`gablue`** (comme l'ISO) — le dialogue le rappelle et ne redémarre pas lui-même. Le dialogue se ferme après avoir lancé la tâche (modal via `exec()`, il désactiverait la fenêtre de progression) ; rouvrir l'outil montre la demande en attente. Le menu MokManager utilise le clavier du firmware, pas la disposition choisie dans Gablue : le mot de passe n'utilise que des lettres à la même position en QWERTY US et en suisse français. L'état Secure Boot figure dans le résumé **« Matériel et système »** de l'onglet local (`secure_boot_state`, aucun privilège) — pas sur la carte, où il faisait doublon.
- **Redémarrer dans le BIOS** (`Redémarrer dans le BIOS…` du menu **Configuration**) : confirmation explicite puis `sudo -n /usr/bin/systemctl reboot --firmware-setup` (règle sudoers exacte) — le menu du firmware (BIOS/UEFI) s'ouvre au démarrage, le démarrage normal reprend à sa fermeture ; poste sans EFI → message, rien n'est lancé.
- **Compression Btrfs** (`Compression Btrfs…` du menu **Configuration**, `dialogs/btrfs.py`) : une case par **point de montage Btrfs** (pas par disque : `/var` et `/var/home` sont deux sous-volumes du même SSD, avec chacun son drapeau). L'état vient de `btrfs property get <montage> compression`, appliqué par `sudo -n /usr/libexec/gablue-btrfs-compress zstd|none <montage>` (règles sudoers exactes ; le helper revérifie que le chemin est bien un montage Btrfs listé par `findmnt`). Le drapeau vaut pour les **nouveaux** fichiers, le dialogue le dit — les données existantes ne sont pas recompressées. À distance (`BtrfsDialog(parent, host=…)`) : montages et compression lus par `REMOTE_BTRFS_PROBE` (`findmnt -J` puis une ligne `COMP` par montage), application par `btrfs_remote_script` en `sudo -n` (mot de passe seulement sans règle NOPASSWD).
- **Limite thermique NVMe** (`Limite thermique NVMe…` du menu **Configuration**, `dialogs/thermal.py`) : une carte par contrôleur `/dev/nvmeN`, case « limiter » + preset (65/70, 70/75, 75/80 °C, « minimum supporté » selon `mntmt`, ou seuils personnalisés). Le helper `/usr/libexec/gablue-nvme-thermal` fait la lecture (`id-ctrl`, `get-feature -f 0x10`) et l'écriture (`set-feature -s`, persistante) : trois sous-commandes exactes au sudoers, bornes revérifiées côté root (TMT1 ≥ `mntmt`, TMT1 < TMT2, plages 40…85 / 45…90). Un contrôleur sans HCTM ou illisible est affiché, jamais modifiable, et un contrôleur dont HCTM est **désactivé** l'est aussi : le firmware impose ses seuils, `mntmt` (souvent 83 °C) est déjà au niveau du throttle, donc une limite réglée ici ne protégerait rien (07/11/2026) — seule une limite déjà posée reste décochable, pour rendre la main au firmware. À distance (`ThermalDialog(parent, host=…)`) : `REMOTE_NVME_THERMAL_PROBE` rend le JSON du helper lu en root (ou `NO_HELPER`), `nvme_thermal_remote_script` applique les trois sous-commandes exactes ; sans helper sur le poste, l'outil est grisé.
- **Limite de température CPU** (`Limite de température CPU…` du menu **Réglages**, `dialogs/ryzen.py`) : proposée **seulement** si `ryzenadj` et un CPU AMD Ryzen sont présents (`local.ryzenadj_available`, lu dans `/proc/cpuinfo`) — inutile ailleurs. Case « limiter » + presets 85/90/95 °C ou valeur libre (45…110), un seul « Appliquer » ; la lecture et l'écriture passent par `/usr/libexec/gablue-ryzenadj` en `sudo -n` (`status`, `set <n>`, `off`, bornes revérifiées côté root). Le helper écrit `/etc/gablue/ryzenadj.conf` et active `gablue-ryzenadj.service` (oneshot), qui réapplique `ryzenadj -f` à **chaque démarrage** : contrairement à l'autostart de `limitw --save`, la limite ne dépend pas de l'ouverture de session. Réglage **local uniquement** ; il ne touche pas au TDP, qui reste le domaine de `limitw`.
- **Nettoyer le système** (`Nettoyer le système…` du menu **Configuration**, `dialogs/clean.py`) : **une carte par domaine, un bouton « Vider » par carte** — pas de sélection multiple : chaque outil se vide seul, après une confirmation qui rappelle l'effet et le gain estimé. Domaines, dans l'ordre affiché : cinq **caches régénérables** d'abord — gwine temp (`~/.cache/gwine/temp`), shaders (`~/.cache/gwine/shader-cache`), WGP (`~/.cache/wgp-extra`), LGP (`~/.cache/lgp-extra`), npm d'OpenCode (`~/.cache/opencode/npm`) — puis les outils lourds en fin de liste : **Podman** (`podman system prune -a --volumes -f` : images, conteneurs arrêtés, réseaux, cache et volumes non utilisés), **Flatpaks** inutilisés (compte en utilisateur + système par `/usr/libexec/gablue-clean flatpak`) et **Homebrew** (`autoremove` + `cleanup`). rpm-ostree (`cleanup -bm`) et le cache gwine complet ont été retirés de l'outil. Jamais les sauvegardes (`~/.local/share/lgp-saves`, `~/.local/share/opencode`), la configuration ni les artefacts de build de `~/.cache/opencode`. Les tailles sont mesurées **en fond** (`du -sb`, `podman system df --format json`), ligne par ligne ; celles que l'outil ne sait pas donner (Flatpaks, Homebrew) affichent **`?`**, et le pied de page montre le total mesuré. Le dialogue s'ouvre **non modal** (`show()`, instance unique conservée par la fenêtre) : il reste affiché pendant qu'une ou plusieurs tâches tournent, sans désactiver leurs fenêtres de progression (`exec()` rendait le dialogue modal et « Fermer » inerte, vécu 07/11/2026). En fin de tâche, `completed` met la ligne à jour sans bloquer la boucle GUI : remesure en fond en local (`du -sb`), taille « ? » et cache devenu indisponible à distance — jamais de sonde SSH synchrone dans ce slot. Le dialogue a deux **onglets** (`QTabWidget`) : « Nettoyage » (les domaines) et « Anciennes versions Syncthing » (`dialogs/stversions.py`, `StVersionsSection`) ; ce second onglet n'existe que si **Syncthing tourne** : dossiers `.stversions` déclarés par `config.xml` (`versionsPath` sinon `<dossier>/.stversions`, bac à sable Flatpak inclus ; repli `~/Syncthing/*/.stversions`), taille de chacun (`du -sb`, en fond, total compris) et **clic → Dolphin** sur le dossier — rien n'y est supprimé. **À distance** (`CleanDialog(parent, host=…)`) : la même liste vient d'une sonde SSH unique (`REMOTE_CLEAN_PROBE` : outils, caches, `du -sb`, `podman system df`), sans section Syncthing (elle appartient à la session locale) ; le mot de passe n'est demandé que pour la partie système des Flatpaks si `gablue-clean` existe sans règle NOPASSWD.
- **Variante de l'image** (`Variante de l'image…` du menu **Configuration**, dialogue d'`dialogs/variant.py`) : liste `REBASE_VARIANTS` (main, main-dx, nvidia, nvidia-open, nvidia-open-dx), libellé « variante actuelle » / « variante inconnue », et bouton **« Basculer »** actif seulement si la variante choisie diffère de `local_variant()` (`rpm-ostree status --json`, déploiement `booted`, `gablue-<variante>` dans la référence d'image) ; confirmation explicite, téléchargement de l'image, effet au redémarrage. Helper `gablue-rebase` absent de l'image → bouton désactivé avec « helper absent — reconstruction requise » (`rebase_helper_available`).
- **Options de gwine** (`Options de gwine…`, local et distant) : lit `~/.local/share/gwine/options` (`dxvk_mode`, `display_mode`, `xbox_default`, SSH pour un poste distant) et applique par gwine lui-même — `gwine --dxvk-async|--dxvk`, `gwine --wayland|--x11`, `gwine --xbox-on|--xbox-off` (tout ou rien ; le filtre `--xbox-ds4`/`--xbox-dualsense` reste en CLI) : le fichier garde son format et le préfixe reçoit les DLL DXVK correspondantes. Conseil affiché sur DXVK (standard, pas d'async) et l'affichage (X11 plutôt que Wayland natif) ; **les manettes en mode Xbox 360 n'en ont pas** (préférence du joueur). Effet au prochain lancement de jeu, aucun privilège, journal en direct.
- **Priorité au premier plan** (`Priorité au premier plan…`, local et distant) : ex-`ujust foreground-booster-enable/disable`, refait sans passer par ujust — `kwriteconfig6 --file kcgroupsrc --group 'Foreground Booster' --key autostart true|false` puis `systemctl --user restart|stop plasma-foreground-booster.service` (best-effort : à distance sans bus de session, le fichier reste ce qui compte à la prochaine connexion). Recommandé : activé.
- **Tailscale** (`Tailscale…`, local et distant) : case activée/désactivée, état lu en une seule commande (`systemctl is-enabled|is-active tailscaled`, `tailscale debug prefs` pour le serveur). À l'activation, le lien du **serveur de connexion** est demandé (`QInputDialog`, prérempli avec le serveur déjà configuré) et validé (`http://` ou `https://`, sans espace ni guillemet) : contrairement à `ujust tailscale-up`, aucun serveur n'est codé en dur. Application par `/usr/libexec/gablue-tailscale on --login-server URL|off` (NOPASSWD) : `tailscale up --operator=$SUDO_USER`, service + firewall en `on`, arrêt + désactivation en `off`. **Aucune pastille de conseil** : Tailscale est un opt-in (on l'utilise ou pas), il n'y a pas de « bon » réglage à recommander. Quand le poste est connecté, le dialogue affiche **le réseau et le nom** (`parse_tailscale_status` : `CurrentTailnet.MagicDNSSuffix`, nom `Self.DNSName` sans le suffixe MagicDNS ni le point final (« gigafed », pas « gigafed.tail.io »), première `TailscaleIPs`, plus le serveur de contrôle tiré de `tailscale status --json`, lu sans privilège par la sonde `TAILSCALE_STATE_SCRIPT`).
- **Barres des configurations** : les fenêtres de réglages (noyau, services, variante, options gwine, booster, Tailscale — **locales et distantes**) et les tâches de la section **Applications** (installation/mise à jour, suppression, configuration ES-DE — locales et distantes) adoptent la présentation des mises à jour : barre de progression, journal **masqué** derrière « Terminal », révélé automatiquement en cas d'échec (`reveal_log_on_error` en local ; à distance le mode `busy` le fait déjà). Le mode est explicite (`progress_mode="busy"` pour une barre indéterminée, `progress_parser` quand la commande publie des étapes) : les **kargs** restent **non progressifs** (un seul déploiement rpm-ostree, aucune progression mesurable) ; **Services et pilotes** a une vraie barre par domaine, `local.system_apply_script` émettant `::gablue:step n total libellé` (total = domaines réellement modifiés) et `::gablue:done` ; variante = indéterminée (téléchargement rpm-ostree muet). `tasks._display_command` résume un script `bash -c` multi-ligne en `<script>` dans l'en-tête du journal, au lieu d'y déverser le script et ses lignes de protocole.
- **Enregistrement Tailscale** : `tailscale up` lancé en root n'ouvre pas de navigateur — il écrit le lien d'authentification sur sa sortie. `local.find_auth_url` retient le **dernier** lien de la sortie en écartant le serveur de connexion (le chemin varie : Tailscale `/a/…`, headscale `/register/…`), `tasks._AuthLinkRow` l'affiche dans la fenêtre (cliquable, bouton **« Copier le lien »**), et `local.tailscale_registered` (sonde `tailscale status --json`, toutes les 1,5 s) constate `BackendState == "Running"` : le lien disparaît alors et le libellé passe à « Appareil enregistré. ». « Annuler » coupe `tailscale up` (SIGTERM puis SIGKILL) et masque le lien. À distance, le lien est extrait de la sortie SSH (pas de sonde) et masqué à la fin.
- **Confirmations courtes** (`QMessageBox.question`) : une ligne qui dit le geste et sa cible, puis au plus une ligne d'effet réel (redémarrage, sessions coupées, réversibilité). Le fonctionnement interne (comment `gwine --init` compare les versions, règles sudoers, détails de bootc) va dans le journal ou l'infobulle — jamais dans la confirmation ; et le sous-titre des fenêtres de tâche parle lui aussi à l'utilisateur, sans ligne de commande (`Runner Wine et composants`, pas `gwine --init — …`). Vécu 07/11/2026 : paragraphes explicatifs et `--init` affichés jugés « moches » par l'utilisateur final.
- **Opérations simultanées** (`start_task`) : chaque opération (mise à jour, redémarrage, réglages, copie de clé) est une fenêtre **non modale** rattachée à la fenêtre principale — plusieurs postes peuvent être traités en même temps, et la fenêtre principale reste utilisable. Les dialogues de configuration se ferment après « Appliquer » et laissent la tâche tourner ; `_tasks` garde les fenêtres vivantes, `completed` déclenche le rafraîchissement des cartes. Un `exec()` (modale) ne doit plus servir qu'aux dialogues qui rendent un résultat immédiat (ajout/édition de poste, choix de candidats).
- **Privilèges** : `privileged_prefix()` sonde `sudo -n /usr/libexec/gablue-cpuid-emu status` (0 = règle NOPASSWD présente) puis retombe sur `pkexec` (dialogue PolicyKit) — `sudo -n true` échouait toujours, même sur Gablue, et faisait passer toute action root par PolicyKit malgré la règle sudoers. **Même piège à distance** : `remote_sudo_nopasswd()` sonde `sudo -n gablue-cpuid-emu status`, seul helper dont `status` sort 0 quelle que soit la configuration ; `sudo -n true` n'a aucune règle, et `gablue-auto-update status` sort 1 dès qu'un timer est désactivé — un poste aux mises à jour coupées passait pour « sans règle NOPASSWD » et réclamait le mot de passe pour redémarrer, éteindre ou faire `bootc upgrade` pourtant autorisé. Les réglages noyau, émulation CPUID, services, couche Vulkan, pilote Wi-Fi, mises à jour automatiques, rebase et Tailscale n'utilisent ni l'un ni l'autre : ils passent par les helpers `/usr/libexec` en `sudo -n` (sans invite). Serveur SSH et annonce locale ont leurs règles exactes (systemctl sshd, `gablue-avahi`), redémarrage/extinction distants aussi (`systemctl reboot|poweroff`). Aucune commande root n'est lancée sur le thread GUI.
- **Actions externes** : `gremote [-p port] user@host` (port non standard) et `dolphin sftp://user@host:port/` (IPv6 entre crochets). Lancement détaché (`start_new_session`) : fermer la fenêtre ne tue pas la session RDP ; sortie capturée et affichée seulement si le code retour est ≠ 0, sauf le 131 de `sdl-freerdp` (fermeture normale de la fenêtre RDP) et les arrêts demandés depuis l'app.
- **Journal** (`journal.py`) : **aucun fichier**, aucune rotation — les journaux de tâche restent en mémoire (bornés par Qt) et le seul log durable est celui de systemd. On y écrit les **échecs de tâche** (`RemoteTaskDialog`/`LocalTaskDialog`/`SequentialTaskDialog`, avec code retour et 4 000 derniers caractères), les **exceptions non attrapées** (`install_excepthook` au démarrage) et l'échec d'une sonde de mises à jour (une fois par processus et par domaine, avec le code retour et la fin de la sortie) ; **jamais les sondes qui réussissent** ni les passages périodiques. Protocole natif `/run/systemd/journal/socket` (`SYSLOG_IDENTIFIER=gablue-manager`, `PRIORITY=3`, `GABLUE_CODE`), repli sur `/dev/log` ; toute erreur d'envoi est silencieuse. Lecture : `journalctl --user -t gablue-manager -b`. Anti-spam maison, en plus du `RateLimitBurst` de journald : même première ligne + même priorité → une seule entrée par 10 min, et 200 entrées maximum par processus (la dernière annonce la coupure) — un bug qui boucle ne peut donc pas noyer le journal. Piège du protocole : le datagramme **doit** finir par un saut de ligne, sinon journald perd le dernier champ (constaté 07/11/2026 — `GABLUE_CODE` disparaissait ; revérifier si journald évolue).
